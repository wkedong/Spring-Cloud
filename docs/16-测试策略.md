# 16 · 测试策略

> 模块：`springboot-basics/`（8010）——本仓库**唯一**能在 `mvn test` 里全绿跑完的模块：15 个用例、0 失败、0 跳过。
> 对照：其它 6 个测试类的 `contextLoads` 全部 `@Disabled`（原因见下文「测试与外部依赖」）。

## 学什么

测试不是「写完补的作业」，而是**把口头承诺变成可执行断言**。本仓库有三类可复用的样本：

| 层次 | 本模块样本 | 用例数 | 耗时 | 启动了什么 |
| --- | --- | --- | --- | --- |
| 单元测试（纯逻辑） | `AuditLogger.record` / `recentRecords` 行为 | 1 | 毫秒 | 什么都不起 |
| **切片测试** | `web/UserControllerTest`（`@WebMvcTest`） | 5 | **0.4~0.6s** | 只起 MVC 组件，无 DB/注册中心 |
| 集成测试（`@SpringBootTest` + H2） | `SpringBootBasicsApplicationTests` | 3 | 2.7~3.1s | 完整上下文 + H2 + Actuator |
| 集成测试 | `service/TransferServiceTest` | 4 | 0.8~1.1s | 完整上下文（独立一份） |
| 集成测试 | `service/ProductServiceCacheTest` | 3 | 4.8~4.9s | 完整上下文（独立一份） |


**15 = 1 + 5 + 3 + 3 + 3**（纯逻辑用例 = `SpringBootBasicsApplicationTests.auditLoggerRecordsToBuffer`，
只断言 `AuditLogger` 的内存缓冲；表中该类的 3 个用例含它）。`UserControllerTest` 5 个用例是全模块最快的
0.4s，集成测试 3s 起步——这就是「金字塔」在工程上的真实含义：**能用切片验证的，绝不拉起整个应用**。

## 核心代码

### 切片测试：只加载一层，毫秒级完成

```java
@WebMvcTest(controllers = {UserController.class, DemoController.class})
@EnableConfigurationProperties(BasicsProperties.class)   // 切片不带配置类，必须显式引入
@Import(CacheConfig.class)                               // Framework 7 缓存 fail-fast，见下方第 3 点
class UserControllerTest {
    @Autowired private MockMvc mockMvc;
    @MockitoBean private UserService userService;        // 依赖被替换成 Mock（@MockBean 在 Boot 4 已删除）
    @Test
    void 未带token返回401与统一响应体() throws Exception {
        mockMvc.perform(get("/api/users")).andExpect(status().isUnauthorized())
                .andExpect(jsonPath("$.code").value(40100));
    }
}
```

`@WebMvcTest` **只**加载 MVC 相关组件：`@Controller`/`@RestController`/`@ControllerAdvice`、`Filter`、
`HandlerInterceptor`、`WebMvcConfigurer` 以及 `@MockitoBean`；**不**加载 `@Service`/`@Repository`/JPA/
数据源/注册中心。六点：

- **Boot 4 升级要点（本仓库实测踩过）**：`@WebMvcTest` 换了包名——现在是
  **`org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest`**，且它所在的 **`spring-boot-webmvc-test`**
  模块**不会**被 `spring-boot-starter-test` 传递引入，pom 里必须显式加这个依赖（本仓库在根 pom 统一声明）；
- **`@MockBean` 已删除**：替代品是 **`@MockitoBean`**（`org.springframework.test.context.bean.override.mockito.MockitoBean`），
  用法不变、import 换掉即可；
- **Framework 7 的缓存 fail-fast**：主类上的 `@EnableCaching` 让缓存切面在**启动时**就要拿到 `CacheManager`，
  而切片会滤掉 `@Configuration`（`CacheConfig` 不在切片范围）——Framework 7 起缺了它**直接启动失败**
  （旧版本是延迟到首次调用才报错，所以这个坑以前看不出来），必须 `@Import(CacheConfig.class)` 之类显式补齐；
- **`MockMvc` 走完整链路**：不经过真实网络，但 Filter → Interceptor → ControllerAdvice 全都会执行——本模块
  `TraceIdFilter`、`AuthInterceptor`、`GlobalExceptionHandler` 都在切片范围内，于是两个「看起来只有集成才能
  测」的行为在切片里就测到了：**401 鉴权**（第 1 个用例）与**字段级校验错误**（第 3 个用例，4 个字段一次断完，
  验证的不只是 `@Valid` 生效，还有错误信息的可读性——前端直接展示它）；
- **为什么需要 `@EnableConfigurationProperties(BasicsProperties.class)`**：`AuthInterceptor` 依赖
  `BasicsProperties`，而配置类**不在**切片范围。**切片报 `NoSuchBeanDefinitionException` 时，先问「这个类
  为什么不在切片范围内」**，而不是急着 `@Import` 整个启动类；
- **`@MockitoBean` 的代价**：测试只关心「请求进 → 响应出」，Controller→Service 的接线正确性测不到（见思考点）。

### 集成测试的取舍

```java
@SpringBootTest(properties = "basics.cache.ttl=60s")        // 只覆盖需要变的配置
class ProductServiceCacheTest { /* ... */ }
@SpringBootTest(properties = {                               // 一份属性 = 一份上下文缓存键
        "basics.environment=from-test", "basics.retry.max-attempts=7",
        "basics.audit.prefix=[TEST-AUDIT]", "basics.cache.ttl=60s"})
class SpringBootBasicsApplicationTests { /* ... */ }
```

**① `webEnvironment` 选择**：默认 `MOCK`（不起真实容器，最快），需要真实 HTTP 端口时才用
`RANDOM_PORT`/`DEFINED_PORT`；本模块全用默认值——`MockMvc` + 真实上下文已够验证行为，起真端口只是更慢。

**② 上下文缓存**：Spring 按「配置类 + 属性 + profile」缓存上下文，**键不同就重新起一份**；本模块 3 个
`@SpringBootTest` 属性各不相同，于是确实起了 3 份（日志实测）：

```
HikariPool-1/2/3 - Starting...   ← 依次对应 SpringBootBasicsApplicationTests / TransferServiceTest / ProductServiceCacheTest
```

`UserControllerTest` 是切片、**没有 Datasource**，所以不占连接池编号。结论：**为合并上下文而无脑统一
`properties`，可能让用例失去隔离性**；正确做法是让属性差异集中且有理由。**③ 不要用 `@Transactional` 掩盖
真实事务边界**：`TransferServiceTest` 验证的正是「回滚」与「自调用失效」，若测试自己再包一层事务，
两个用例都会「通过」——但什么都没证明：

```java
@Test
void 入账后抛异常时整个事务回滚() {
    assertThatThrownBy(() -> transferService.transferWithFailure(1L, 2L, new BigDecimal("100")))
            .isInstanceOf(BusinessException.class).hasMessageContaining("演示用异常");
    // 失败发生在「已扣款 + 已入账」之后，但事务回滚，两边余额必须保持原值
    assertThat(balanceOf(1L)).isEqualByComparingTo("1000.00");
    assertThat(balanceOf(2L)).isEqualByComparingTo("500.00");
}
```

数据一致性改由 `@BeforeEach` 重置（测试类上**没有** `@Transactional`）。**真实踩过的坑**：`Account` 带
`@Version`，若 `new Account(id, balance)` 直接 `save()`，`version` 为 `null` 会被判为新对象而走 `persist`，
**余额根本没被重置**，测试可能因上一次数据恰好正确而飘过。正确姿势是「先查再改」托管实体：`findById(1L)`
→ `setBalance(new BigDecimal("1000.00"))` → `saveAndFlush(...)`。

### 不稳定测试的治理：别断言绝对耗时

`ProductServiceCacheTest` 是「给时间相关行为写断言」的范本：

```java
assertThat(productService.getLoadCount()).isEqualTo(before + 1);   // 真实执行次数不增长（缓存命中）
assertThat(firstCost).isGreaterThanOrEqualTo(700L);                 // 只断言量级（真实慢查询 800ms）
assertThat(secondCost).isLessThan(100L);                            // 只断言量级，不写「必须 <5ms」
assertThat(secondCost).isLessThan(firstCost);                       // 相对比较，机器无关
```

- **不断言具体毫秒数**：CI 机器慢 / 本地跑着 Docker，`<5ms` 必然假失败；700ms / 100ms 的阈值刻意留了余量
  （真实值 800ms / 3ms）；
- **把 TTL 调大**：测试用 `basics.cache.ttl=60s`（生产 yml 是 `5s`），避免用例执行中缓存自然过期——
  **测试里凡是「等待类」参数都往安全方向调**；
- **缓存跨用例共享**：同一上下文里 `CacheManager` 是同一个 Bean，每个用例第一行先 `productService.evictAll()`。

### 测试与外部依赖：`@Disabled` 不是答案，三种更好的做法

`grep -rn "@Disabled" --include=*.java .` 共 8 处命中、去注释后 6 个测试类（逐字输出见「动手验证」第 4 步），
原因是它们都需要 eureka(6060)/config(6010) 在线（`service-producer` 还要 MySQL 3306，`FeignServiceTest`
还要 service-producer 6070）。

**为什么跳过**：这些模块的 `application.yml` 要连 Eureka 6060、并经 `spring.config.import` 拉 Config 6010，
`@SpringBootTest` 在**上下文启动阶段**就去拉配置，外部组件不在线时是**启动失败而非断言失败**，报错与「被测代码有问题」完全无关；显式跳过
并写明原因，比让它一直红着、或不写理由地跳过都要好。三种更好的做法（按推荐度）：

| 做法 | 怎么落地 | 适用场景 | 代价 |
| --- | --- | --- | --- |
| Testcontainers | `@Container` 起 MySQL/Redis/注册中心镜像，容器就绪后再起上下文 | 需要真实数据库语义（Flyway 迁移、方言、锁） | 本机要有 Docker，首次拉镜像慢 |
| `@MockitoBean` 掉远程依赖 | 把 `DiscoveryClient`/远程 Client 换成 Mock，只测本模块逻辑 | 测「编排逻辑」而非「远程是否可用」 | Mock 与真实行为可能漂移，需契约测试兜底 |
| profile 指向内存实现 | 测试用 `application-test.yml` 把 DB 换 H2、关掉注册中心 | 快速回归，长期可跑 | 与生产环境差异最大 |

本模块是第 3 种的完整示范（H2 + 无注册中心），所以 `contextLoads` 是**真跑**而不是跳过；它还顺带用集成测试
守住了自定义 starter 的自动配置契约（能注入 `AuditLogger`、`basics.audit.prefix` 绑定到 `[TEST-AUDIT]`）
——见 [15-自动配置与自定义Starter](15-自动配置与自定义Starter.md)。

### 断言与可读性

- **AssertJ 优先于 JUnit 原生断言**：`assertThat(x).isEqualByComparingTo("900.00")` 比
  `assertEquals(new BigDecimal("900.00"), x)` 失败信息清楚得多，`BigDecimal` 还常因精度不同给出误导性失败；
- **测试方法用中文名**（本仓库统一做法）：`void 入账后抛异常时整个事务回滚()`，Surefire 报告里直接是可读
  句子，定位比 `testTransferRollbackCase2` 快得多；
- **一个用例一个行为**：`TransferServiceTest` 把「正常转账」「异常回滚」「余额不足」「自调用失效」拆成 4 个
  方法，失败时不用猜哪个分支坏了；**异常断言要断类型 + 消息片段**，只断类型会漏掉「抛错了地方」。

## 思考点

- **切片会不会漏 bug**：`@MockitoBean` 替掉了 `UserService`，「Controller 传参正确但 Service 抛异常」测不出来。
  你怎么划定切片测试的**责任边界**，又用什么保证 Service 自己也被测过？
- **上下文缓存与状态污染**：为复用上下文而统一 `properties`，会让不同测试类共享静态变量、缓存与单例 Bean
  的残留状态——`@DirtiesContext` 是解药还是毒药（它对总耗时的影响有多大）？
- **为什么不用 `@Transactional`**：本模块故意不用，代价是数据靠 `@BeforeEach` 手工重置。若被测逻辑涉及
  **异步线程里的事务**或**多数据源**，`@Transactional` 回滚还有效吗？
- **`@Disabled` 的债务**：6 个被跳过的测试类会随时间腐化（接口变了也没人知道）。你会优先把哪一个改造成
  Testcontainers，判断依据是什么？
- **测试的性价比**：`ProductServiceCacheTest` 花 4.8s（占全量 40%）只验证 3 条缓存行为。CI 分钟数受限时
  你会怎么加速——调小 `sleepQuietly` 的时长会不会让断言失去意义？
