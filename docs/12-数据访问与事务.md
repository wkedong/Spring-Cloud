# 12 · 数据访问与事务：JPA、内存库与事务边界

> 模块：`springboot-basics/`（8010，H2 内存库，零外部依赖），启动见 [09-本地运行指南](09-本地运行指南.md)。
> 相关：[11-配置体系](11-配置体系.md) 讲配置怎么进来，本篇讲数据怎么写进去、写坏了怎么回滚；测试取舍见 [16-测试策略](16-测试策略.md)。

## 学什么

`@Transactional` 是 Spring 里「看起来最简单、出错最隐蔽」的注解：加了不等于生效，抛异常不等于回滚。本篇用两个账户的转账，把三件事变成 curl 就能看到的事实：

| 行为 | 入口 | 结果 |
| --- | --- | --- |
| 正常提交 | `POST /api/tx/transfer` | 1000/500 → 900/600 |
| 异常回滚 | `POST /api/tx/transfer-fail` | HTTP 400，余额仍是 900/600 |
| 同类自调用 → 事务失效 | `POST /api/tx/self-invocation` | **不报错**，余额变成 850/650（数据被改坏） |

## 核心代码

### 1. 实体与仓库：JPA 的最小闭环

```java
@Entity @Table(name = "account")
public class Account {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id;
    @Column(nullable = false, precision = 18, scale = 2) private BigDecimal balance;  // 金额绝不用 double
    @Version private Long version;                                                    // 乐观锁
}
public interface UserRepository extends JpaRepository<User, Long> {
    List<User> findByNameContaining(String name);   // 方法名即查询 → like '%name%'
    boolean existsByEmail(String email);            // 只关心「有没有」，比 find 少一次实体组装
}
```
派生查询用方法名表达简单条件（可读、不用写 JPQL 字符串），多条件/联表/投影再退回 `@Query`；`UserService.create` 用 `existsByEmail` 挡重复邮箱，就是「语义即方法名」的典型用法。

### 2. 为什么是 H2，`ddl-auto` 怎么选

datasource 就是一行 `jdbc:h2:mem:basics;DB_CLOSE_DELAY=-1;MODE=MySQL`：内存库随进程消失、`mvn test` 不需要任何外部组件；`MODE=MySQL` 让语法贴近 MySQL，换真库时只改这一段（`config/` 模块是 MySQL + Flyway 的形态）。

| `ddl-auto` | 行为 | 用在哪 |
| --- | --- | --- |
| `none` | 什么都不做 | 结构由迁移工具管（生产首选） |
| `validate` | 只校验，不一致就启动失败 | 生产：迁移与实体不一致要早暴露 |
| `update` | 增量改表（加列可以，改列/删约束不行） | 本地开发，别上生产 |
| `create` / `create-drop` | 启动重建 / 关闭时删 | 集成测试、教学（本模块默认 `create-drop`） |

### 3. `data.sql` 的两个坑

**坑一：Boot 2.5+ 必须开 `defer-datasource-initialization: true`。** 否则 `data.sql` 在 EntityManagerFactory 之前执行，Hibernate 还没建表 → 报表不存在（脚本初始化与结构初始化抢跑）；打开后 SQL 初始化被推迟到建表之后。

**坑二：显式指定主键后，自增序列不会自己前进。**

```sql
INSERT INTO sys_user (name, email, phone, age, created_at) VALUES ('张三', …);  -- 种子数据 id 由 H2 生成 = 1
ALTER TABLE sys_user ALTER COLUMN id RESTART WITH 100;                         -- 必须手动推
```
H2/MySQL 不会因为「你手工插了 id=1、2」就把 identity 计数器推到 3，后续 JPA 插入仍会生成 id=1 → 主键冲突（`Duplicate entry '1' for key 'PRIMARY'`）。实测按这份种子数据启动后创建新用户返回 `"id":100`：既证明序列确实被推到了 100，也说明这两行 `ALTER` 不能省。（换个角度看，`create-drop` 与 `data.sql` 让「结构的真相」有两个地方在改，生产只应保留迁移工具。）

### 4. `open-in-view: false` 为什么必须关

Boot 默认 `OpenEntityManagerInView=true`：把 EntityManager 绑到请求线程，**等到序列化 JSON 时才**触发懒加载。代价是：①`@Transactional(readOnly = true)` 的边界形同虚设——SQL 发在事务之外；②数据库连接被持有到响应结束，连接池被「渲染 JSON」占住；③`LazyInitializationException` 在单测里见不到、上线才见。关掉后所有数据访问都必须发生在事务/仓库方法内，问题在开发期就暴露。本模块实体还没有关联（暂时踩不到懒加载），这个开关是「以后加关联别踩」的防线。

### 5. 金额与并发：`BigDecimal` + `@Version`

- 金额用 `BigDecimal`（`0.1 + 0.2 != 0.3` 的浮点误差在账务上是事故）；比较用 `compareTo` 而不是 `equals`：`new BigDecimal("900.0").equals(new BigDecimal("900.00"))` 为 false（scale 不同）。
- `@Version` 乐观锁防**丢失更新**：两个事务都读到 version=0，先提交的把它改成 1；后提交执行 `UPDATE ... WHERE id=? AND version=0` 影响 0 行 → 抛 `ObjectOptimisticLockingFailureException`。宁可让这一笔失败重试，也不能让后一笔把前一笔的余额覆盖掉；代价是热点账户并发失败率上升——生产要么配重试，要么改成原子 `UPDATE balance = balance - ?`，要么上悲观锁。

### 6. 事务的三种可实测行为（本文重点）

```java
@Transactional(rollbackFor = Exception.class)        // ① 正常转账：扣款 + 入账同一个事务
public Map<String, Object> transfer(Long fromId, Long toId, BigDecimal amount) { doTransfer(...); … }

@Transactional(rollbackFor = Exception.class)        // ② 入账后抛异常 → 整笔回滚
public Map<String, Object> transferWithFailure(...) { doTransfer(...); throw new BusinessException(…); }

public Map<String, Object> transferSelfInvocationBroken(...) {   // ③ 外层**没有** @Transactional
    try {
        doTransferInTransactionalMethod(fromId, toId, amount);   // this. 调用 → 不经过代理
        throw new BusinessException("演示用异常：应为事务失效，扣款不会回滚");
    } catch (BusinessException ex) { log.warn("自调用场景捕获异常：{}", ex.getMessage()); }
    return snapshot("self-invocation-broken", fromId, toId, amount);
}
@Transactional(rollbackFor = Exception.class)
public void doTransferInTransactionalMethod(...) { doTransfer(...); }   // 注解在这里，但没人生效
```
原理一句话：`@Transactional` = AOP 代理，**外部**调用先过代理（开启事务），`this.foo()` 是对象内部直连，代理被绕过，注解退化成注释。`@Async`、`@Cacheable` 的自调用是同一个坑——本模块缓存演示里的 `GET /api/cache/products/1/self-invocation` 每次都真实执行 800ms 慢查询、命中不了缓存，原因完全一致（见 [13-缓存异步与定时任务](13-缓存异步与定时任务.md)）。

### 7. 事务失效排查清单与修复

| 现象 | 原因 | 修复 |
| --- | --- | --- |
| 注解完全不生效 | 同类自调用（`this.xxx()`） | 抽到另一个 Bean；或 `TransactionTemplate`；或 `AopContext.currentProxy()`（需 `exposeProxy=true`，代码变丑，不推荐） |
| 抛了异常却已提交 | `rollbackFor` 默认只回滚 `RuntimeException`/`Error`，受检异常不回滚 | 显式写 `rollbackFor = Exception.class`（本模块每个写方法都写了） |
| 根本没进事务 | 方法是 `private`/`final`/`static`，或类不是 Spring Bean | 改 `public` 并交给容器管理；`final` 生成不了代理 |
| 异常被 catch 吞掉 | 事务拦截器收不到异常 → 正常提交 | catch 里重新抛出，或 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()` |
| 内层想独立提交却跟着回滚 | `REQUIRED` 会加入外层事务 | 用 `REQUIRES_NEW`，且必须经过代理调用 |

编程式事务最不依赖代理，适合「一小段一定要独立提交」的逻辑：`transactionTemplate.execute(status -> { doTransfer(fromId, toId, amount); return null; });`

| 传播 | 行为 | 什么时候用 |
| --- | --- | --- |
| `REQUIRED`（默认） | 有就加入，没有就新建 | 绝大多数业务方法 |
| `REQUIRES_NEW` | 挂起外层，自己独立提交/回滚 | 审计/日志/消息投递：不能因为外层回滚而丢 |
| `NESTED` | 保存点，内层回滚不影响外层（外层回滚仍全回滚） | 批量处理里「单条失败不拖累其它条」 |
| `SUPPORTS` | 有就加入，没有就以非事务方式执行 | 只读查询 |
| `NOT_SUPPORTED` / `NEVER` | 挂起 / 禁止事务 | 长耗时外部调用，别占着数据库连接 |
| `MANDATORY` | 必须已有事务，否则抛异常 | 强制「只能被事务方法调用」的内部方法 |

> 最危险的组合是「自调用 + `REQUIRES_NEW`」：你以为开了新事务，实际连事务都没有。

### 8. 测试写法：为什么测试类不要加 `@Transactional`

`TransferServiceTest` 用 `@SpringBootTest` 却**故意不加** `@Transactional`：

```java
@Test void 入账后抛异常时整个事务回滚() {
    assertThatThrownBy(() -> transferService.transferWithFailure(1L, 2L, new BigDecimal("100")))
            .isInstanceOf(BusinessException.class);
    assertThat(balanceOf(1L)).isEqualByComparingTo("1000.00");    // 回滚后必须保持原值
    assertThat(balanceOf(2L)).isEqualByComparingTo("500.00");
}
```
给测试类加 `@Transactional`，每个方法就跑在一个外层事务里并自动回滚：服务层的 `@Transactional` 变成「加入外层事务」，**回滚断言永远通过**——哪怕业务方法一个事务注解都没写；「自调用失效」留下的脏数据也会被外层回滚悄悄擦掉。**测试包事务 = 把要验证的东西删掉**，数据隔离改用 `@BeforeEach` 重置。

重置数据的坑（本模块踩过）：带 `@Version` 的实体必须「先查出来再改」——

```java
Account account = accountRepository.findById(id).orElseThrow(...);   // 先查 → 拿到托管实体
account.setBalance(new BigDecimal("1000.00"));
accountRepository.saveAndFlush(account);
```
若写成 `new Account()` + `setId(1L)` + `save(...)`：`version` 为 null，`save()` 判定为**新对象**而走 `persist`，重置静默失效，测试之间互相污染、断言「偶尔」失败。带乐观锁/审计字段的实体永远「先查再改」。

15 个用例的分工（`mvn -B -pl springboot-basics -am test` 全绿）：上下文与 starter 自动配置 3（`SpringBootBasicsApplicationTests`，用 `@SpringBootTest(properties = …)` 覆盖配置）、Web 切片 5（`@WebMvcTest` + MockMvc）、事务 4（本类，真事务真回滚）、缓存 3。

## 动手验证

```bash
export JAVA_HOME=$(/usr/libexec/java_home -v 17)
java -jar springboot-basics/target/springboot-basics-0.0.1-SNAPSHOT.jar     # 8010，H2 内存库 + data.sql

H='X-Token: dev-token'; B=http://127.0.0.1:8010
curl -s -H "$H" $B/api/tx/accounts
# {"code":0,...,"data":{"1":{"owner":"张三","balance":1000.00},"2":{"owner":"李四","balance":500.00}}}

curl -s -X POST -H "$H" "$B/api/tx/transfer?fromId=1&toId=2&amount=100"
# account1.balance=900.0 / account2.balance=600.0        ← 一个事务里扣款 + 入账

curl -s -i -X POST -H "$H" "$B/api/tx/transfer-fail?fromId=1&toId=2&amount=100" | tail -2
# {"code":50000,"message":"演示用异常：入账后主动失败，观察两边余额是否回滚",...}   HTTP 400
curl -s -H "$H" $B/api/tx/accounts
# 仍是 900.00 / 600.00 —— 异常发生在「已扣款 + 已入账」之后，回滚把它们一起撤销

curl -s -X POST -H "$H" "$B/api/tx/self-invocation?fromId=1&toId=2&amount=50"
# {"action":"self-invocation-broken",...}，注意：**没有报错**
curl -s -H "$H" $B/api/tx/accounts
# 850.00 / 650.00 —— 扣款没回滚，数据已被改坏：这就是事务失效的现场

mvn -B -pl springboot-basics -am test        # 把行为钉成断言
# Tests run: 15, Failures: 0, Errors: 0, Skipped: 0
```

## 思考点

- 自调用失效最可怕的地方是「代码评审时看着完全正确」。除了抽 Bean / `TransactionTemplate`，有什么机制能在**合入前**发现它？（断言「异常后余额不变」的测试、启动期扫描同类自调用的自检、ArchUnit 规则……）
- 热点账户扣减你会怎么选：`@Version` 乐观锁 + 重试、原子 `UPDATE balance = balance - ?`、`SELECT ... FOR UPDATE` 悲观锁，还是 Redis 预扣 + 异步落库？各自的一致性边界和失败模式是什么？
- 关掉 `open-in-view` 后，`@Transactional` 边界画在 Service 还是 Controller？DTO 组装放事务内还是事务外？为什么「事务里发远程调用 / 投 MQ」是事故？（提示：连接被占住、提交与消息不在同一个原子域）
- 迁移脚本（Flyway）与实体不一致时，`ddl-auto: validate` 让应用启动失败，是好事还是阻塞发布？在你们的发布流程里，谁负责改表、谁来卡住这次上线？
- `UserService.getById` 同时挂了 `@Cacheable` 与 `@Transactional(readOnly = true)`：缓存命中时方法体不执行，事务也就开不出来——这对读路径是好事；但两个注解都是 AOP，先后顺序会影响「事务里做缓存写」这类判断，你有办法确定它们的实际顺序吗？（提示：两个 Advisor 的 `order`、观察是否真的获取了连接）
