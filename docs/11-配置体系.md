# 11 · 配置体系：多环境、类型安全绑定与优先级

> 模块：`springboot-basics/`（8010，H2 内存库，零外部依赖），启动见 [09-本地运行指南](09-本地运行指南.md)。
> 关联：starter 的 `basics.audit.*` 同走这套机制（[15-自动配置与自定义Starter](15-自动配置与自定义Starter.md)）；配置中心见 [02-配置中心](02-配置中心.md)。

## 学什么

配置事故大多不是「写错」，而是**不知道哪一行真正生效**：默认文件一份、profile 文件一份、命令行再传一个，最后用的是哪个？本篇用一套 `basics.*` 回答三件事：

| 要解决的问题 | 手段 | 本模块落点 |
| --- | --- | --- |
| 多环境差异 | `application.yml` + `application-{profile}.yml` | `application-dev.yml`、`application-prod.yml` |
| 配置散落、类型靠约定 | `@ConfigurationProperties` 集中绑定 | `config/BasicsProperties.java` |
| 配错了怎么发现 | `@Validated` + JSR-303 启动期校验 | `web/ConfigController.java` 读当前生效值 |

## 核心代码

### 1. 多环境：默认值 + profile 只写差异

```yaml
# application.yml
spring:
  profiles:
    active: dev                      # 默认激活；--spring.profiles.active=prod 可覆盖
basics:
  environment: ${BASICS_ENV:local}    # 占位符 + 默认值
# application-dev.yml（只写差异）
basics:
  environment: dev
```
切换：`--spring.profiles.active=prod`、`SPRING_PROFILES_ACTIVE=prod`、测试 `@ActiveProfiles("prod")`。prod 的差异都是「运维行为」而非业务语义：

| 维度 | dev | prod |
| --- | --- | --- |
| 日志 | `debug` + Hibernate SQL | root `warn` 并落文件（logback-spring.xml 分环境） |
| H2 控制台 | 开 | 关 |
| `ddl-auto` | `create-drop` | `validate` |
| Actuator | `env/configprops/beans/threaddump` 全开 | 只留 `health,info,metrics,prometheus` |

> **实测坑**：`--spring.profiles.active=prod` 在本模块 H2 内存库上**起不来**：`SchemaManagementException: Schema-validation: missing table [account]`——`ddl-auto: validate` 在 EntityManagerFactory 构建阶段校验表结构，而 `data.sql` 要等 `defer-datasource-initialization` 之后才执行，空库 validate 必然失败（生产敢用 `validate` 的前提是结构先由迁移工具建好）。

### 2. `@ConfigurationProperties` vs `@Value`

```java
@ConfigurationProperties(prefix = "basics")
@Validated
public class BasicsProperties {
    @NotBlank private String appName = "springboot-basics";
    private Map<String, Boolean> features = new LinkedHashMap<>();   // 一个开关控制多个特性
    private List<String> contacts = new ArrayList<>();
    private Retry retry = new Retry();                              // 嵌套对象
    public static class Retry { @Min(1) private int maxAttempts = 3; private Duration backoff; }
}
```

| 能力 | `@Value("${basics.retry.backoff}")` | `@ConfigurationProperties(prefix="basics")` |
| --- | --- | --- |
| 松散绑定 | 不支持，键名必须逐字写对 | `app-name` ↔ `appName` 自动映射 |
| 类型安全 | 自己保证（收成 String，用时才炸） | `Duration`/`List`/`Map`/嵌套对象直接绑 |
| 批量 | 一个字段一行注解 | 一个类绑一整棵配置树 |
| 校验 | 无，只能 `@PostConstruct` 手写判断 | 类上 `@Validated` + JSR-303 |
| IDE 提示 | 无 | `configuration-processor` 生成元数据 json（补全、默认值提示） |
| 动态刷新 | 逐字段处理 | 配合配置中心 `@RefreshScope` 整体刷新 |

实测「yml 写什么、绑出来什么」（`GET /api/config` 摘要）：`"retry.maxAttempts": 3`、`"retry.backoff": "PT0.2S"`、`"cache.ttl": "PT5S"`、`"cache.maxSize": 100`——yml 里写的是 `200ms`/`5s`，绑成 `Duration` 后 `toString()` 是 ISO-8601（`PT0.2S`），不带单位的数字按毫秒解释（换单位用 `@DurationUnit`）。starter 的 `basics.audit.*`（`prefix`/`maxDetailLength`/`slowThreshold`/`level`）与业务配置同等待遇：使用方不写装配代码就能注入 `AuditLogger`。

### 3. 配置校验：让错误在启动期爆炸

`BasicsProperties` 上有 `@NotBlank private String appName`（空白即失败）与 `@Min(1) private int maxAttempts`。实测 `--basics.retry.max-attempts=0`（进程**根本不会起来**）：

```
APPLICATION FAILED TO START
Binding to target ... BindException: Failed to bind properties under 'basics' ... failed:
    Property: basics.retry.maxAttempts
    Value: "0"
    Origin: "basics.retry.max-attempts" from property source "commandLineArgs"
    Reason: 最小不能小于1
```
空白值同样拦得住：`SPRING_APPLICATION_JSON='{"basics":{"app-name":""}}'` → `Property: basics.appName / Reason: 不能为空`。报错自带 **Origin（哪个属性源）与 Value**，这是它比手写 `if (x == null) throw` 值钱的地方：启动期失败只是「一次部署失败」（K8s 里就是 CrashLoop，一眼可见），漏到运行期则是「某个请求走到那行代码才 NPE」，可能几天后才暴露，还要靠 traceId 反查。

### 4. 配置优先级

`GET /api/config/priority` 把带 `basics.` 前缀的属性源按 Spring 的查找顺序打印出来，实测：

```
orderedSources[0] = 'class path resource [application-dev.yml]'   basics.environment = "dev"
orderedSources[1] = 'class path resource [application.yml]'       basics.environment = "${BASICS_ENV:local}"…
resolvedEnvironment = "dev"    # hint: 列表按优先级从高到低，命令行参数与环境变量排在最前
```
列表顺序就是优先级，**先命中的赢**；完整顺序（由高到低）：

| 顺序 | 来源 | 例子 |
| --- | --- | --- |
| 1 | 命令行参数 | `--basics.environment=from-cli` |
| 2 | `SPRING_APPLICATION_JSON` | `SPRING_APPLICATION_JSON='{"basics":{"environment":"x"}}'` |
| 3 | Java 系统属性 / OS 环境变量 | `-Dbasics.environment=x`、`BASICS_ENVIRONMENT=x`（松散绑定） |
| 4 | jar 外部/内部的 `application-{profile}.yml` | 本模块 `application-dev.yml`（部署目录 `config/` 下的同名文件更优先） |
| 5 | jar 外部/内部的 `application.yml` | 本模块 `application.yml` |
| 6 | `@PropertySource`、测试 `@SpringBootTest(properties=…)` | 上下文测试里 `basics.environment=from-test` |
| 7 | 代码里的字段默认值 | `private int maxAttempts = 3` |

实测命令行覆盖：加 `--basics.environment=from-cli` 后列表最前面多出 `commandLineArgs` 源（`basics.environment = from-cli`），`resolvedEnvironment` 变成 `from-cli`——它盖掉了 `application-dev.yml` 里的 `dev`，因为命令行参数排在任何文件之前。

> **占位符不是独立的属性源（真坑）**：`${BASICS_ENV:local}` 只是「在写它的那个文件里做一次替换」，结果仍受该文件自身优先级约束。实测 `BASICS_ENV=from-env java -jar ...` 启动后 `basics.environment` 仍是 `dev`（`application-dev.yml` 硬写了 `environment: dev` 且优先级更高）；换成 `BASICS_ENVIRONMENT=from-env`（环境变量直接命中 `basics.environment`，是第 3 档的独立来源）才生效，`resolvedEnvironment = from-env`。同一机制下 `BASICS_TOKEN=env-token` 生效，因为 `security-token` 只在 `application.yml` 里定义过一次。结论：想让环境变量说话，profile 文件里就别硬写同名键。

### 5. 占位符、bootstrap 与配置中心

`basics.security-token: ${BASICS_TOKEN:dev-token}`：`:` 后是默认值，无默认值且解析不到就是启动失败。Boot 2.4 起 `bootstrap.yml` **默认不再加载**，Spring Cloud 曾为此提供 `spring-cloud-starter-bootstrap`：它在 application 上下文之前先起 bootstrap 上下文，好让「从配置中心拉配置」发生在 Bean 装配之前；**升级到 Spring Cloud 2025.1 后这条路径已废弃**，`bootstrap.yml` 与 `spring-cloud-starter-bootstrap` 都已从各模块（`service-producer/`、`zuul/` 等）退场，统一改走 Config Data API 的 `spring.config.import`：

```yaml
spring:
  config:
    import: optional:configserver:http://localhost:6010/   # optional: = 配置中心不可用也能启动
```

拉取时机同样在 Bean 装配之前，语义等价。到了配置中心优先级模型不变：远端配置集仍按「应用名 + profile」分组下发，本地文件降级为兜底默认值，最前面的依旧是命令行参数与环境变量——这正是容器里用环境变量覆盖镜像内配置的原理。

> **`spring.config.import` 的优先级（实测）**：被导入的配置中心配置**优先于**导入它的本地 `application.yml`；
> 同一应用里写多条 `import` 时，**后写的赢**。

细节见 [02-配置中心](02-配置中心.md) 与 `nacos-demo/`。

## 生产注意点

- **敏感配置不要给可用的默认值**：`${BASICS_TOKEN:dev-token}` 的默认值是为教学可跑而留的；生产若忘了注入环境变量，应用会拿着 `dev-token` 正常启动——「能跑起来的错误」比启动失败危险得多。生产应外部化（环境变量 / K8s Secret / 密钥管理服务）并让缺失表现为启动失败。
- **端点泄露**：教学配置把 `env,configprops,beans,threaddump` 全开了，`/actuator/env` 列出所有属性源与配置项、`/actuator/configprops` 列出所有绑定对象，够画出内部拓扑；脱敏只按 key 名匹配 `password/secret/token` 这类关键词，命名不巧就漏。prod 已收紧为 `health,info,metrics,prometheus` + `show-details: when-authorized`，更进一步是挂独立端口（`management.server.port`）并加认证。
- **配置变更要留痕**：`POST /actuator/loggers/...` 能不改代码就改运行期日志级别（实测把 `AuthInterceptor` 调到 `TRACE` 立即生效、无需重启），配置中心的推送同理：谁在什么时候改了哪个开关，必须有审计与可回滚版本。

## 动手验证

```bash
export JAVA_HOME=$(/usr/libexec/java_home -v 17)
java -jar springboot-basics/target/springboot-basics-0.0.1-SNAPSHOT.jar     # 8010，默认 dev

# 当前生效的配置（含 starter 的 basics.audit.*）
curl -s -H 'X-Token: dev-token' http://127.0.0.1:8010/api/config
# environment=dev、security-token=dev-token、retry.maxAttempts=3、retry.backoff="PT0.2S"、
# cache.ttl="PT5S"、cache.maxSize=100、activeProfiles=["dev"]

# 谁覆盖了谁
curl -s -H 'X-Token: dev-token' http://127.0.0.1:8010/api/config/priority
# orderedSources[0]=application-dev.yml(environment=dev) → [1]=application.yml(${BASICS_ENV:local})

# 命令行参数排最前（换端口另起进程，避免影响 8010）
java -jar springboot-basics/target/springboot-basics-0.0.1-SNAPSHOT.jar \
  --server.port=8011 --basics.environment=from-cli
curl -s -H 'X-Token: dev-token' http://127.0.0.1:8011/api/config/priority
# orderedSources[0]=commandLineArgs(basics.environment="from-cli")，resolvedEnvironment=from-cli

# 配错就启动失败（进程不会起来）
java -jar springboot-basics/target/springboot-basics-0.0.1-SNAPSHOT.jar --basics.retry.max-attempts=0
# Property: basics.retry.maxAttempts / Value: "0" / Reason: 最小不能小于1

# 功能开关
curl -s -H 'X-Token: dev-token' http://127.0.0.1:8010/api/config/features/tx-demo
# {"feature":"tx-demo","enabled":true,"allFeatures":{"cache-demo":true,"async-demo":true,"tx-demo":true}}
```

## 思考点

- `dev-token` 这种「带默认值的敏感配置」：prod 忘了注入时你希望**启动失败**还是"凑合跑"？若选前者，怎么用 `@Validated` + profile 表达「prod 必须显式提供 token」？
- 排查「为什么是这个值」还有哪些手段？`/api/config/priority` 只列了 `EnumerablePropertySource`，而环境变量源**没有**出现在列表里，为什么？（提示：它的键名是 `BASICS_ENVIRONMENT`，不带 `basics.` 前缀）
- 配置热更新（Nacos/Config + `@RefreshScope`）会带来哪些新问题：正在处理的请求读到半新半旧的配置？单例 Bean 里的配置字段要不要 `volatile`？`@RefreshScope` 代理后的注入点有什么禁忌？
- `ddl-auto: validate` 与 `data.sql` 在空库上冲突（本模块 prod 实测启动失败）：结构与数据初始化该怎么分工？为什么生产用 Flyway/Liquibase 取代它们？
- 把 `env`/`configprops` 开在内网就安全吗？若线上排查确实需要它们，怎么做到「可观测」与「不泄露」兼得？
