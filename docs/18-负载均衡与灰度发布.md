# 18 · 负载均衡与灰度发布：自定义 LoadBalancer 与负载均衡层重试

> 模块：`service-consumer-ribbon/`（7030，RestTemplate + `@LoadBalanced`）。前置阅读：[03-服务消费](03-服务消费.md)、[01-服务注册与发现](01-服务注册与发现.md)。

## 学什么

Ribbon 已在 2021.0.x 退役，`@LoadBalanced RestTemplate` 的能力由 **Spring Cloud LoadBalancer** 接管，但它的默认策略只有一个：轮询。真正难的不是「挑一台机器」，而是**按业务规则挑机器**——灰度发布就是最典型的一种。需求：producer 有新版本 v2，只让带灰度标记的流量进 v2，其余流量留在 v1；一旦标记打错（写了个不存在的版本），服务不能整体不可用。

| 要解决的问题 | 机制 | 本模块实现 |
| --- | --- | --- |
| 实例如何自我标记版本 | Eureka `metadata-map.version` | `service-producer/src/main/resources/application-peer*.yml` |
| 怎么按标记挑实例 | 自定义 `ReactorServiceInstanceLoadBalancer` | `service/GrayHeaderLoadBalancer.java` |
| 怎么把策略绑定到某个服务 | `@LoadBalancerClients` + 配置类 | `config/LoadBalancerClientsConfig.java`、`config/GrayLoadBalancerConfiguration.java` |
| 实例列表从哪来、多久刷新一次 | `ServiceInstanceListSupplier` + 缓存 TTL | 同上 + `application.yml` |
| 下游偶发 5xx 自动换个实例重来 | `spring.cloud.loadbalancer.retry.*` | `application.yml` + `spring-retry` 依赖 |

## 核心代码

### 1. 自定义负载均衡器三件套（灰度决策全在 `select()`：命中标记固定那台，否则退回轮询）
```java
public class GrayHeaderLoadBalancer implements ReactorServiceInstanceLoadBalancer {
    private static final String GRAY_HEADER = "X-Gray-Version";
    private static final String VERSION_METADATA_KEY = "version";

    @Override
    public Mono<Response<ServiceInstance>> choose(Request request) {
        ServiceInstanceListSupplier supplier = supplierProvider.getIfAvailable(NoopServiceInstanceListSupplier::new);
        return supplier.get(request).next().map(instances -> select(instances));
    }

    private ServiceInstance roundRobin(List<ServiceInstance> instances) {          // 与官方策略同样的原子计数
        int index = Math.abs(position.getAndIncrement() % instances.size());
        return instances.get(index);
    }
}
```
挑实例时按元数据比对（省略了日志行，实际每个分支都打了日志，这是排查灰度问题的命根子）：

```java
String grayVersion = currentGrayVersion();                    // 从当前 HTTP 请求头 X-Gray-Version 读
if (grayVersion != null) {
    for (ServiceInstance instance : instances) {
        if (grayVersion.equals(instance.getMetadata().get("version"))) {
            logger.info("灰度路由命中：{} -> {}:{} ...", serviceId, instance.getHost(), instance.getPort());
            return new DefaultResponse(instance);
        }
    }
    logger.warn("灰度标记 {} 在 {} 中没有匹配实例，退化为轮询（共 {} 个实例）", grayVersion, serviceId, instances.size());
}
return new DefaultResponse(roundRobin(instances));
```

### 2. 绑定策略：`@LoadBalancerClients` 与**不能加 `@Configuration`** 的配置类

```java
@Configuration
@LoadBalancerClients({
        @LoadBalancerClient(name = "service-producer", configuration = GrayLoadBalancerConfiguration.class)
})
public class LoadBalancerClientsConfig { }
```
```java
public class GrayLoadBalancerConfiguration {          // ⚠️ 故意不加 @Configuration
    @Bean
    public ReactorLoadBalancer<ServiceInstance> grayHeaderLoadBalancer(Environment env, LoadBalancerClientFactory factory) {
        String name = env.getProperty(LoadBalancerClientFactory.PROPERTY_NAME);       // 当前客户端名
        return new GrayHeaderLoadBalancer(factory.getLazyProvider(name, ServiceInstanceListSupplier.class), name);
    }
}
```

### 3. 实例供应器：servlet 栈必须用 blocking

```java
@Bean
public ServiceInstanceListSupplier serviceInstanceListSupplier(ConfigurableApplicationContext context) {
    return ServiceInstanceListSupplier.builder()
            .withBlockingDiscoveryClient()   // ⚠️ servlet 栈必须用它，不是 withDiscoveryClient()
            .withCaching()
            .build(context);
}
```

### 4. 缓存与重试（`application.yml`）

```yaml
spring.cloud.loadbalancer:
  cache:
    ttl: 2s                 # 实例列表本地缓存，默认 35s；调小才能较快看到实例上下线
  retry:
    enabled: true           # 需要 spring-retry 依赖（pom 已加），重试发生在「负载均衡这一层」
    retry-on-all-operations: false           # GET 默认重试；POST 等非幂等操作要显式开
    max-retries-on-same-service-instance: 1  # 同一实例最多再试 1 次
    max-retries-on-next-service-instance: 1  # 或换下一个实例再试 1 次
    retryable-status-codes: 500,502,503,504  # 不配则不会因为状态码而重试
```

## 关键机制与易错点

1. **配置类不能加 `@Configuration`**——加了它就在组件扫描路径下变成父容器的全局 Bean，于是「只对 service-producer 生效」变成**对所有负载均衡客户端生效**，它里面的 `ServiceInstanceListSupplier` 还会和框架的默认供应器抢同一个 Bean（要么被顶掉、要么因禁止 Bean 覆盖而报错，两种情况都不可接受）。这与 Feign 的 `@FeignClient(configuration = X.class)` 是同一个坑。
2. **`ServiceInstanceListSupplier.builder().withDiscoveryClient()` 在 servlet 栈必炸**。实测报错：`NoSuchBeanDefinitionException: No qualifying bean of type 'org.springframework.cloud.client.discovery.ReactiveDiscoveryClient' available`。原因是 `withDiscoveryClient()` 要的是响应式发现客户端（WebFlux 栈），而本模块是 servlet + Eureka 阻塞式客户端。**选择原则：servlet 应用用 `withBlockingDiscoveryClient()`，WebFlux/响应式应用用 `withDiscoveryClient()`。**
3. **灰度标记要放在 `metadata-map` 而不是端口/实例名**。端口和实例名是「部署事实」，会随扩缩容变；`metadata-map` 是「逻辑标签」，能在不改代码、不改部署结构的前提下把任意实例划进灰度组（`version: v1/v2/v3`，同一份配置换 profile 即可）。而且注册中心、网关、Feign、LoadBalancer 全都能读到同一份元数据，标记只需定义一次。
4. **灰度命中失败必须降级，不能报错**。标记写错（比如 `v9`）、灰度组还没扩容出来，都属于**预期的运营态**：此时退回轮询，服务仍然可用，只有日志里留一条 WARN。反过来，如果这里抛异常，一次配置手误就变成全站故障。
5. **`cache.ttl` 决定了你多久才能看到实例上下线**。默认 35s 意味着新实例注册后最长 35s 才进候选列表——灰度发布时「明明扩容了却没流量」多半就是它。生产上不要一味调小（每次失效都要打注册中心），按发布节奏取几秒到十几秒。
6. **负载均衡层重试不是 Feign 层重试**。这一层由 `RetryLoadBalancerInterceptor` + `spring-retry` 实现，作用于 `@LoadBalanced RestTemplate` 的 HTTP 调用；Feign 客户端另有自己的 `Retryer`。两层都开就是乘法（3×2=6 次下游调用），**只应保留一层**。另外重试只在 GET（幂等）上默认生效，`retry-on-all-operations: true` 会让下单/支付这类请求被重复发送。
7. **灰度标记要能下传到全链路**。服务端应该把自己识别的灰度标记回写进链路上下文（Micrometer Tracing 的 Baggage，见 docs/21），否则中间服务一跳转发就丢了标记，请求又落回老版本。

## 动手验证

服务已在运行（7030 ribbon、6070/6080 producer），以下均为只读命令。

```bash
# ① 先看实例清单与灰度元数据的来源：两个实例，metadata.version 分别是 v1 / v2
curl -s http://127.0.0.1:7030/lb/instances
# {"serviceId":"service-producer","instanceCount":2,"instances":[
#   {"instanceId":"192.168.85.52:service-producer:6070","port":6070,"metadata":{"zone":"zone-a","version":"v1"}},
#   {"instanceId":"192.168.85.52:service-producer:6080","port":6080,"metadata":{"zone":"zone-b","version":"v2"}}], ...}

# ② 不带灰度头：严格轮询 6080 → 6070 → 6080 → 6070 …
for i in 1 2 3 4 5 6; do curl -s http://127.0.0.1:7030/testGray; echo; done
# 第1次 port=6080 version=v2 / 第2次 6070 v1 / 第3次 6080 v2 / 第4次 6070 v1 / 第5次 6080 v2 / 第6次 6070 v1

# ③ 带 X-Gray-Version: v2：三次全落 6080（v2 实例），带 v1：三次全落 6070
for i in 1 2 3; do curl -s -H 'X-Gray-Version: v2' http://127.0.0.1:7030/testGray; echo; done
for i in 1 2 3; do curl -s -H 'X-Gray-Version: v1' http://127.0.0.1:7030/testGray; echo; done
# 期望：带 v2 的三次 port 全为 6080；带 v1 的三次 port 全为 6070 —— 灰度标记完全压过轮询

# ④ 灰度标记不存在（v9）：应退化为轮询而不是报错
curl -s -H 'X-Gray-Version: v9' http://127.0.0.1:7030/testGray; echo
curl -s -H 'X-Gray-Version: v9' http://127.0.0.1:7030/testGray; echo
# 第1次 port=6080 version=v2 / 第2次 port=6070 version=v1 —— 与不带标记时同样的轮询序列

# ⑤ 每个决策都有日志：命中/轮询/退化三态（grep 出的原样记录）
grep -E '灰度路由命中|轮询选中|没有匹配实例' /tmp/up-smoke/logs/service-consumer-ribbon.log | tail -14
# INFO  c.w.s.s.r.s.GrayHeaderLoadBalancer : 轮询选中：service-producer -> 192.168.85.52:6080 (metadata.version=v2)
# INFO  c.w.s.s.r.s.GrayHeaderLoadBalancer : 灰度路由命中：service-producer -> 192.168.85.52:6080 (metadata.version=v2)
# WARN  c.w.s.s.r.s.GrayHeaderLoadBalancer : 灰度标记 v9 在 service-producer 中没有匹配实例，退化为轮询（共 2 个实例）
# INFO  c.w.s.s.r.s.GrayHeaderLoadBalancer : 轮询选中：service-producer -> 192.168.85.52:6080 (metadata.version=v2)
```

到这里为止曲线是干净的：`灰度路由命中` 与 `轮询选中` 严格互斥，v9 那次是「先 WARN 再轮询」，两条日志同属一个 traceId。

```bash
# ⑥ 负载均衡层重试：producer 每个实例的「第一次」调用必 500，重试后成功
curl -s http://127.0.0.1:7030/testLbRetry
# {"success":true,"producerResponse":{"port":6080,"attempt":2,"success":true},
#  "hint":"producerResponse.attempt > 1 说明负载均衡层重试确实重发了一次请求","costMillis":6}
# 再打一次（计数器已过 1，不再产生失败，因此也看不到重试）：
curl -s http://127.0.0.1:7030/testLbRetry
# {"success":true,"producerResponse":{"port":6070,"attempt":3,"success":true}, ...}

# ⑦ producer 侧收到的两次调用（同一 traceId、同一实例 6080、相隔 3ms）
grep 'testRetry' /tmp/up-smoke/logs/producer-6070.log /tmp/up-smoke/logs/producer-6080.log | tail -6
# producer-6080.log: INFO c.w.s.s.s.impl.ProducerServiceImpl : /testRetry 第 1 次调用（port: 6080, success: false）
# producer-6080.log: INFO c.w.s.s.s.impl.ProducerServiceImpl : /testRetry 第 2 次调用（port: 6080, success: true）
```

⑥⑦ 一起看才是完整证据链：消费端只发了一次 HTTP 请求，producer 侧却收到两条调用记录（第 1 次 `success:false` 触发 500，第 2 次成功），`attempt: 2` 就是这个事实的「回执」。**注意这个演示只对每个实例的第一次调用有效**：`ProducerServiceImpl` 里是一个进程级 `AtomicInteger retryCounter`，计数器一旦超过 1 就永远成功，所以重试效果只在**服务刚启动后的第一次请求**能观察到（复核实测后续调用一律 `success: true`，`attempt` 只是继续往上累加，不构成重试证据）；要反复复现必须重启 producer——这也是「用计数器造故障」的通用缺陷。

## 思考点

1. 灰度路由为什么不能直接用 Ribbon 的 `NFLoadBalancerRule` 或官方 `RoundRobinLoadBalancer` 改一改？把「按请求头挑实例」写进自定义负载均衡器，与写成网关路由规则（docs/19 的 `GrayRoute` 之类）各有什么代价和适用面？
2. `GrayHeaderLoadBalancer` 用 `RequestContextHolder` 读请求头，所以只在处理 HTTP 请求的线程里有效。如果调用发起自定时任务、MQ 消费线程或 `@Async`，这个灰度标记会怎样？还能不能用同一套机制？
3. 标记打错（`v9`）退化为轮询，服务可用但灰度策略静默失效——这种「温和降级」和「直接报错」哪个更危险？你会怎么让它在监控上可见，而不是只在日志里躺一条 WARN？
4. `spring.cloud.loadbalancer.cache.ttl` 默认 35s，灰度发布时它会让「新扩容的 v2 实例收不到流量」多久？如果把它调成 0 会发生什么？
5. 负载均衡层重试与 Feign 层重试同时开启时，一次用户点击会放大成几次下游调用？为什么 `retry-on-all-operations` 默认是 `false`？哪些接口即便失败也绝不该重试？
6. 灰度标记只加在请求头上，一旦经过一个不转发该头的中间服务就丢失了。要让标记贯穿整条链路（网关 → 消费方 → 生产方），你会把它放在请求头、Baggage（docs/21）还是消息头里？各自能覆盖哪些调用方式？
