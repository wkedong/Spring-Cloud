# 29 · 容器化部署：镜像分层、compose 编排与无 Docker 验证

> 模块：整仓；交付物在 `deploy/`（`Dockerfile`、`docker-compose.yml`、`docker-compose-nacos.yml`、`README.md`）。
> 前置阅读：[09-本地运行指南](09-本地运行指南.md)、[21-配置刷新与链路追踪进阶](21-配置刷新与链路追踪进阶.md)、[24-Nacos注册与配置](24-Nacos注册与配置.md)。
> ⚠️ 本机没有 Docker daemon（只有 Homebrew 的 `docker-compose` 客户端），镜像与编排**没有真正跑起来过**；
> 但分层、健康检查探针、环境变量绑定都在本机实测过，未能核实之处见文末与 `deploy/README.md` 第五节。

## 学什么

这个仓库一直是「`java -jar` + 手工按顺序起进程」：16 个模块、11 个端口，代价很具体——顺序靠记忆、
环境靠改 `bootstrap.yml`、换台机器从头再来一遍。容器化要解决三件事：

| 问题 | 做法 | 在 `deploy/` 里的落点 |
| --- | --- | --- |
| 「改一行代码，镜像要重传 70MB」 | 镜像分层，只重传变化的那层 | `Dockerfile` 里四行 `COPY --from` |
| 「谁先起、谁等谁」 | healthcheck + depends_on | `docker-compose.yml` |
| 「容器里的 localhost 是它自己」 | 配置外置成环境变量/参数 | 同一份 compose 的 `environment` 段 |

## 核心代码

### 1. Dockerfile：多阶段 + 分层拷贝

构建阶段用 Maven 镜像出 jar，顺手做分层提取；运行阶段只带 JRE，按层 `COPY`：

```dockerfile
FROM maven:3.9-eclipse-temurin-17 AS builder
ARG MODULE=service-producer
COPY . .
RUN mvn -B -pl ${MODULE} -am -DskipTests package
RUN java -Djarmode=layertools -jar ${MODULE}/target/*.jar extract --destination /workspace/extracted

FROM eclipse-temurin:17-jre AS runtime
COPY --from=builder --chown=app:app /workspace/extracted/dependencies/          ./
COPY --from=builder --chown=app:app /workspace/extracted/spring-boot-loader/   ./
COPY --from=builder --chown=app:app /workspace/extracted/snapshot-dependencies/ ./
COPY --from=builder --chown=app:app /workspace/extracted/application/          ./
USER app
ENTRYPOINT ["sh", "-c", "exec java $JAVA_OPTS org.springframework.boot.loader.JarLauncher \"$@\"", "--"]
```

三处细节值得单独说：**构建上下文必须是仓库根目录**（多模块工程 `-pl <module> -am` 时仍要能读到根
`pom.xml` 与全部子模块 `pom.xml`）；**`--destination <dir>` 必须用空格分隔**（写成 `--destination=<dir>`
会报 `Unknown option` 且**退出码仍是 0**，详见易错点）；启动类换成 `JarLauncher`——此时 `/app` 下已经是
被拆开的分层目录，不再有 fat jar 可跑，而 `"$@"` 让 `docker run <image> --server.port=6071` 这类参数能追加进去。

### 2. docker-compose.yml：编排与启动顺序

10 个服务，端口与仓库真实配置一一对应：

| 服务 | 模块目录 | 端口 | 健康检查 |
| --- | --- | --- | --- |
| mysql | 官方 `mysql:8.0` | 3306 | `mysqladmin ping` |
| zipkin | 官方 `openzipkin/zipkin:3` | 9411 | 无（见易错点） |
| eureka | `eureka` | 6060 | `/actuator/health` |
| config | `config` | 6010 | 配置中心 REST `/service-producer/dev/develop` |
| producer-peer1 / peer2 | `service-producer`（profile `peer1`/`peer2`） | 6070 / 6080 | `/actuator/health` |
| consumer-feign / ribbon / hystrix | 三个消费者模块 | 7020 / 7030 / 7040 | `/actuator/health` |
| gateway | `zuul`（目录名沿用历史名，实现是 Spring Cloud Gateway） | 6050 | `/actuator/health` |

顺序靠声明式依赖串起来，和 [09-本地运行指南](09-本地运行指南.md) 里「eureka → config → 业务」的裸机顺序一致：

```yaml
config:
  depends_on:
    mysql:  { condition: service_healthy }
    eureka: { condition: service_healthy }
producer-peer1:
  environment:
    SPRING_PROFILES_ACTIVE: peer1                 # profile 只能从外部传，见易错点
    SPRING_DATASOURCE_URL: jdbc:mysql://mysql:3306/spring_cloud_demo?...
    EUREKA_CLIENT_SERVICEURL_DEFAULTZONE: http://eureka:6060/eureka/
    SPRING_CLOUD_CONFIG_URI: http://config:6010/
```

### 3. jarmode=layertools：本机实测

本机没有 Docker，就在有 JDK 17 的机器上把「镜像构建时执行的命令」单独跑一遍：

```bash
export JAVA_HOME=$(/usr/libexec/java_home -v 17)
$JAVA_HOME/bin/java -Djarmode=layertools -jar service-producer/target/service-producer-0.0.1-SNAPSHOT.jar list
# → dependencies / spring-boot-loader / snapshot-dependencies / application  （顺序即缓存顺序）
$JAVA_HOME/bin/java -Djarmode=layertools -jar service-producer/target/service-producer-0.0.1-SNAPSHOT.jar \
    extract --destination /tmp/layers-demo
du -sk /tmp/layers-demo/*
#  96  application              （20 个文件：BOOT-INF/classes、bootstrap.yml、META-INF、layers.idx）
# 71036 dependencies            （151 个文件：BOOT-INF/lib 里的第三方 jar，占绝对大头 ≈ 69M）
#   0  snapshot-dependencies    （0 个文件：本仓库没有 SNAPSHOT 外部依赖，目录是空的）
# 408  spring-boot-loader       （68 个文件：org/springframework/boot/loader 启动器）
```

`BOOT-INF/layers.idx` 里的规则就是 `COPY` 顺序的依据：`dependencies → BOOT-INF/lib/`、
`spring-boot-loader → org/`、`snapshot-dependencies →（空）`、`application → BOOT-INF/classes/` 等。

所以「改一行业务代码」只会让 `application` 层（96K）失效、`dependencies` 层（69M）命中缓存——这就是分层的理由。

## 关键机制与易错点

**JVM 容器感知**：不设堆上限时 JVM 按**宿主机**内存算，容器里很容易被 OOMKilled。镜像默认给
`JAVA_OPTS="-XX:MaxRAMPercentage=75.0 -Duser.timezone=Asia/Shanghai -Dfile.encoding=UTF-8"`
（JDK 11+ 的容器感知 `UseContainerSupport` 默认开启），覆盖只需 `-e JAVA_OPTS=...`；留 25% 给元空间、线程栈和堆外内存。

**健康检查**：有 actuator 的模块统一探 `/actuator/health`（`health` 端点默认就暴露，不必额外配 `exposure`）。
两个例外：`config` 模块**没有引 actuator**，改用配置中心自带的 REST 接口 `/service-producer/dev/develop`
——它会真的查一次 MySQL，比探端口更能证明「配置中心可用」；`zipkin` 干脆不写 healthcheck（官方镜像里
可用的 HTTP 客户端不确定），它是上报型依赖，掉了只丢 span，没有服务 `depends_on` 它。

**时区**：`ENV TZ=Asia/Shanghai` + 装 `tzdata` + `-Duser.timezone` + JDBC URL 的 `serverTimezone=Asia/Shanghai`，四处都要照顾，少一处就出现「日志时间比 Zipkin 少 8 小时」。

**环境变量绑定**：容器里 `localhost` 指向容器自己，必须覆盖 `bootstrap.yml` 里的 `localhost:6060`/`localhost:6010`。
本机用 Spring Boot 的 `ConfigurationPropertySources` 实测了几种写法：

| 目标属性 | 环境变量 | 结果 |
| --- | --- | --- |
| `spring.zipkin.base-url` | `SPRING_ZIPKIN_BASE_URL` / `SPRING_ZIPKIN_BASEURL` | 两种都绑得上 |
| `spring.cloud.nacos.discovery.server-addr` | `..._SERVER_ADDR` / `..._SERVERADDR` | 两种都绑得上 |
| `spring.cloud.nacos.discovery.metadata.instance-port` | `..._INSTANCE_PORT` | ❌ 绑成 `metadata.instance.port` |
| 同上 | `--spring.cloud.nacos.discovery.metadata.instance-port=8211` | ✅ **Map 里的 key 用命令行参数** |

**Flyway 与已有库**：配置中心用 MySQL 时，全新库保持 Flyway 开启即可自动建 `properties` 表；若库里已有表
却没有配套的 `flyway_schema_history`，启动会报 `Duplicate entry '1' for key 'properties.PRIMARY'`
（`V1.1__Update_version.sql` 是显式主键 INSERT，重跑必然撞），此时用 `SPRING_FLYWAY_ENABLED=false`
——与 [21-配置刷新与链路追踪进阶](21-配置刷新与链路追踪进阶.md) 里本机的做法同源。

**profile 传递**：`SPRING_PROFILES_ACTIVE=peer1/peer2` 从外部传，**不能**写在 profile 特定文件里
（Boot 2.4+ 会直接启动失败）；也别和 compose 自己的 `profiles:` 混淆，后者决定「哪些服务被启动」。

最后一条是踩坑记录：`extract --destination=<dir>` 会报 `Unknown option ... for the extract command`，
但**退出码依然是 0，而且报错打印在 stdout 而不是 stderr 上**（实测 stdout 297B / stderr 0B）。
也就是说 CI 里写 `... || exit 1` **抓不到这个失败**，必须写成 `--destination <dir>`，或额外校验提取目录的
文件数。顺带说：`extract` 会自动创建目标目录（无需先 `mkdir`），也可以只抽指定层
（`extract --destination <dir> application`，实测 20 个文件）。

## 动手验证

本机没有 Docker，能做的验证是这三类（都已执行）：

```bash
# ① 单模块打包（只动 service-producer，绝不做全仓 mvn clean）
export JAVA_HOME=$(/usr/libexec/java_home -v 17)
mvn -B -q -pl service-producer -DskipTests package          # exit 0
# 注：target 下已有最新 jar 时 maven-jar-plugin（forceCreation=false）不会重复打包，jar 时间戳可能不变，这不是失败。

# ② 把 Dockerfile 里那条分层命令单独跑一遍（等价于镜像构建的 extract 步骤）
java -Djarmode=layertools -jar service-producer/target/service-producer-0.0.1-SNAPSHOT.jar \
     extract --destination /tmp/layers-demo && du -sh /tmp/layers-demo/*

# ③ compose 文件静态校验：docker-compose config 不需要 daemon
docker-compose -f deploy/docker-compose.yml config                                      # exit 0，无告警
docker-compose -f deploy/docker-compose.yml -f deploy/docker-compose-nacos.yml config   # 合并后 13 个服务
```

**没有 Docker 时的部署替代方案**（这个仓库本机就是这么跑的）：直接 `java -jar`，用 systemd 或 supervisor
托管进程、按 `After=`/`priority` 控制启动顺序，配置外置换成 `--spring.cloud.config.uri=` 之类的命令行参数。
容器化真正多给你的是：一致的运行环境、声明式的依赖顺序、以及可以按层增量分发的镜像——所以即使不上 Docker，
`jarmode=layertools` 这套「分层 + 按层传输」的思路仍然可以照搬。

## 思考点

1. 分层的收益来自「层不变则缓存命中」。它什么时候会失效？把 `COPY . .` 放在 `mvn package` 之前对缓存意味着什么？
2. 健康检查探 `/actuator/health` 与探业务接口，哪个更适合判断「就绪」？`depends_on` 保证的是「启动顺序」还是「可用顺序」？
3. 环境变量 vs 命令行参数 vs 挂载配置文件：三种配置外置方式，哪种适合密钥、哪种适合频繁调整的参数？
4. 一个容器里应该跑几个进程？把 MySQL、Eureka、业务服务塞进同一个容器会带来什么问题？
5. 本机这套「`java -jar` + systemd」与容器方案，在滚动发布、回滚、日志采集三件事上分别差在哪里？

## 未能核实之处

`docker build` 与 `docker compose up` **一次都没跑过**（本机没有 daemon，只做了 `docker-compose config` 静态校验）；
基础镜像标签 `maven:3.9-eclipse-temurin-17`、`eclipse-temurin:17-jre`、`openzipkin/zipkin:3` 未实际拉取
（`zipkin` 的 healthcheck 因此故意留空）；容器里的服务注册与调用链未验证。完整清单见 `deploy/README.md` 第五节。
