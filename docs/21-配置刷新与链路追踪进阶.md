# 21 · 配置刷新与链路追踪进阶

> 模块：`service-producer/`（6070=peer1、6080=peer2）；依赖本机 Eureka 6060、Config 6010、MySQL 3306、Zipkin 9411。
> 前置阅读：[02-配置中心](02-配置中心.md)、[07-服务追踪](07-服务追踪.md)、[24-Nacos注册与配置](24-Nacos注册与配置.md)、[09-本地运行指南](09-本地运行指南.md)。

## 学什么

前 20 篇讲「服务之间怎么协作」，剩下两个问题只有真跑起来才会暴露（本篇 JSON、traceId、标签均来自本机实跑）：

1. **配置改了，怎么让进程知道？** 重启最笨，`POST /actuator/refresh` 最直接——但它到底刷新了什么？
   实测答案是：**只刷新被 `@RefreshScope` 标记的 bean**，其他 bean 里的 `@Value` 一动不动。
2. **一条链路里怎么插入自己的步骤？** 自动埋点只看得到「谁调用了谁」，看不到「业务代码内部走了哪几个阶段、
   带没带灰度标识」，这需要自定义 span 与 baggage。

## 核心代码

### 1. 对照实验：同一个 key、两个 bean，一个变一个不变

`config/RefreshableConfig.java`：

```java
@Component @RefreshScope                        // 关键：bean 进入 refresh 作用域
public class RefreshableConfig {
    @Value("${name:unknown}") private String name;   // 来自配置中心（properties 表 key=name）
}
```

`service/impl/ProducerServiceImpl.java` 里另有一个普通字段 `@Value("${name:unknown}") configName`，
它所在 bean **没有** `@RefreshScope`。改库 + `POST /actuator/refresh` 后，`/testConfigRefresh` 实测返回：

```json
{"refreshScopeName":"refresh-demo-new","plainValueName":"test-dev-develop",
 "scope":"bean=RefreshableConfig, applicationName=service-producer"}
```

一个变、一个不变，这不是 bug：`@RefreshScope` 的 bean 在刷新时被**销毁**，下次注入或调用时**重建**，
重建过程重新解析 `@Value` 占位符。

刷新接口返回的 `["name"]` 是**本次发生变化的 key 列表**：只改一个 key 就只有一个元素，改三个就是三个；
没有变更时实测直接返回 **`[]`**（升级后空跑一次 `POST /actuator/refresh` 的结果，说明端点本身是通的）。
值从哪来可查证——`GET /actuator/env/name` 能看到它的值与来源：升级前（bootstrap 时代）实测 source 是
`bootstrapProperties-service-producer-dev`；现在配置中心改用 `spring.config.import: optional:configserver:...`
接入（`bootstrap.yml` + `spring-cloud-starter-bootstrap` 已废弃），属性源名字随之变化，但「值来自配置中心
那一份、而不是本地文件」这个结论不变。
演示完成后已把库里的值还原为 `test-dev-develop` 并再次刷新，见「动手验证」④。

### 2. 配置中心是 MySQL 支撑的 Config Server

`config/src/main/resources/application.yml` 里 `spring.profiles.active=jdbc`，
取数 SQL 为 `SELECT KEY, VALUE from PROPERTIES where APPLICATION=? and PROFILE=? and LABEL=?`，
表在 `spring_cloud_config` 库的 `properties`：

| 列 | 含义 | 本例取值 |
| --- | --- | --- |
| APPLICATION | 服务名 | service-producer |
| PROFILE | profile | dev |
| LABEL | 分支/标签 | develop |
| KEY / VALUE | 配置项 | name / test-dev-develop |

启动配置中心时实测要加 `--spring.flyway.enabled=false`：`schema/V1.1__Update_version.sql` 用显式主键
INSERT 播种数据，表里已有数据时重跑迁移会报 `Duplicate entry '1' for key 'properties.PRIMARY'`
——即 Flyway 与本地已有 MySQL 库的冲突。

### 3. 编程式自定义 span（`ProducerServiceImpl#spanDemo`）

```java
Span span = tracer.nextSpan().name("producer-custom-span").tag("demo.tag", tag).start();
try (Tracer.SpanInScope scope = tracer.withSpan(span)) {
    BaggageInScope baggage = tracer.createBaggageInScope("gray-version", tag);   // Micrometer Tracing 的 API
    try {
        logger.info("自定义 span 内：tag={}, traceId={}, spanId={}", tag,
                span.context().traceId(), span.context().spanId());
    } finally { baggage.close(); }
} finally { span.end(); }              // 必须 end：不 end 就不上报（且内存泄漏）
```

### 4. 注解式自定义 span 依赖 AOP（`service/SpanAnnotatedService.java`）

```java
@Service public class SpanAnnotatedService {
    @Observed(name = "producer-annotated-span", contextualName = "annotated-work")
    public void annotatedWork(String arg) { /* sleep 60ms 便于观察耗时 */ }
}
```

`@Observed`（Micrometer Observation 的注解；Sleuth 的 `@NewSpan`/`@SpanTag` 已随 Sleuth 一起退役）同样靠 AOP
代理实现：**必须**有 `spring-boot-starter-aspectj`（本模块 pom 已声明；Boot 4 里 `spring-boot-starter-aop`
已改名为它），并且要 `management.observations.annotations.enabled: true`（Boot 3.2+ 起注解默认不生效，
打开后自动注册 `ObservedAspect`）——两个条件缺一个，注解就**静默失效**：不报错、也没有 span。同理，同类内部
自调用绕过代理，同样不生效（所以本类被单独抽出来，由 Controller 直接注入调用）。另外 `@Observed` 只支持写在
注解里的**常量**标签；像「按参数打标签」（旧的 `demo.arg`）要用编程式兜底
（`Observation.createNotStarted(...).lowCardinalityKeyValue(...)`）。

### 5. baggage 要报白名单才跨服务

链路追踪自动配置在 Boot 4 里不再随 actuator 一起来，改用 **`spring-boot-starter-zipkin`**（内含
micrometer-tracing、brave 桥接与 Zipkin 上报）。`application.yml` 实测配置：
`management.tracing.sampling.probability: 1.0`（演示期保证每次都能查到），
`management.tracing.baggage.remote-fields` 与 `correlation.fields` 都只声明了一项 `gray-version`——**只有列进
`remote-fields` 的 key 才会写进下游请求头**，`correlation.fields` 只影响本进程 MDC（日志关联字段）。
上报地址的键也换了：`management.zipkin.tracing.endpoint: http://localhost:9411/api/v2/spans`
（要写到 v2 API 路径；Sleuth 时代的 `spring.zipkin.base-url` 只写到主机端口）。

## 关键机制与易错点

Micrometer Tracing 的 API 事实（升级后本仓库 `ProducerServiceImpl` 实测）：`io.micrometer.tracing.Tracer`
同样负责「建 span + 建 baggage」；创建 baggage 用 **`tracer.createBaggageInScope(String name, String value)`**，
返回 `BaggageInScope`（`Closeable`，close 后失效）。注意与 Sleuth 时代的区别：那边叫
`tracer.createBaggage(...)`、**没有** `createBaggageInScope`；迁移时按本仓库写法统一换成
`createBaggageInScope`（照旧文章写会直接编译不过）。

真实 span 证据：一条链路里 3 个 span（Zipkin v2 API 查到；升级后 traceId 是 W3C 的 128 位十六进制）：

| span 名 | 产生方式 | 关键 tags |
| --- | --- | --- |
| `get /testspan` | 服务端自动 | http.path=/testSpan、mvc.controller.class=ProducerController、mvc.controller.method=testSpan |
| `producer-custom-span` | 编程式 | demo.tag=gray-v2 |
| `producer-annotated-span` | `@Observed` 注解式（需 `management.observations.annotations.enabled: true`） | ——（`@Observed` 只支持注解里写死的常量标签，`demo.arg` 这类动态标签要用编程式） |

跨服务透传的证据是**下游回显的请求头**：升级后传播类型默认是 **W3C**，实测回显的是
`traceparent: 00-<traceId>-<spanId>-01`（Sleuth 时代的 `x-b3-*` 4 件套不再自动注入）。而这条链路成立有两个
硬前提——**引入 `feign-micrometer`**、**给 `RestTemplate` 挂上 `ObservationRegistry`**：实测修复前 4 个消费者
在 Zipkin 里都是**单服务 trace**（producer 侧生成新 traceId），修复后各自出现 `[服务A, service-producer]`
的**同一条 trace**（客户端 span 名 `http get`）；查 Zipkin 服务列表当时返回 4 个服务。

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 自定义 span 在 Zipkin 里查不到 | `span.end()` 没执行 | try/finally 保证 end |
| 下游读不到 baggage | key 不在 `remote-fields` | 显式声明白名单 |
| `@Observed` 完全没反应 | 没开 `annotations.enabled` / 缺 aspectj starter / 同类自调用 | 打开开关、加依赖、抽成独立 bean |
| 异步线程里 traceId 为空 | MDC 不跨线程 | 自定义 `TaskDecorator` 复制上下文 |
| Zipkin 查不到某次请求 | `probability` < 1 被采样丢弃 | 演示期设 1.0，生产按量调 |

刷新侧的坑：`/actuator/refresh` 只作用于**收到请求的那个实例**，多实例要逐个调（或上消息总线）；
生产做法是 Spring Cloud Bus（Kafka/RabbitMQ 广播 `RefreshRemoteApplicationEvent`）自动刷新，
或直接用 Nacos 配置监听（见 [24-Nacos注册与配置](24-Nacos注册与配置.md)），Nacos 客户端长轮询无需手动触发。

## 思考点

1. `@RefreshScope` 是「销毁 + 重建」：bean 里若缓存了数据、开了连接、起了线程，重建时谁负责收尾？
2. `/actuator/refresh` 是单实例的。20 个实例怎么刷：逐个 curl、Bus 广播，还是根本不该用 Config？三者的运维成本和一致性窗口各是多少？
3. 为什么 `traceparent` 能自动跨服务，而你自己塞进 MDC 的业务字段不能？哪些信息值得进 baggage 白名单？
4. `probability: 1.0` 在演示环境没问题，生产全量上报的成本落在哪一环：应用、网络还是 Zipkin 存储？采样后「查不到」与「真的没发生」如何区分？
5. 自定义 span 的粒度怎么定：每个方法一个 span 会带来什么后果？何时用 `@Observed`，何时用编程式？
