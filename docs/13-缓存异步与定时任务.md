## 学什么

前面几篇讲「多个服务怎么连起来」，本篇回到**单个应用内部**最常被面试深挖的三件事：缓存（第二次查询从 800ms 变 1ms）、异步（5×300ms 从 1523ms 变 610ms）、定时任务（三行代码，坑在参数与线程池）。三者共用同一个底层机制：**Spring AOP 代理**——注解能否生效，取决于调用是否**穿过代理**，这是本篇反复回到的主线。


## 核心代码
### 缓存抽象：注解是抽象，实现可换

Spring Cache 只提供注解与 `CacheManager`/`Cache` 接口，实现可插拔：

| 实现 | 位置 | 多实例一致性 | 适用 |
| --- | --- | --- | --- |
| **Caffeine**（本模块） | 进程内 | 无（各实例一份） | 单实例、读多写少、能容忍 TTL 内脏读 |
| Redis | 进程外 | 有 | 多实例部署、需要统一失效 |
| 多级（Caffeine + Redis） | 两者 | 一级靠 TTL、二级靠失效广播 | 高并发读，成本最高 |

业务代码只认注解，**换实现不改业务类**；三个关键参数全部由 `BasicsProperties` 驱动（`basics.cache.ttl=5s`、`max-size=100`）：

```java
manager.setCaffeine(Caffeine.newBuilder()
        .expireAfterWrite(properties.getCache().getTtl().toMillis(), TimeUnit.MILLISECONDS) // 写入后过期
        .maximumSize(properties.getCache().getMaxSize())   // 超出按 W-TinyLFU 淘汰（保高频项，优于 LRU）
        .recordStats());                                   // 不开则 cache.* 指标与 CacheStats 全空
manager.setAllowNullValues(false);                         // 不缓存 null，见「穿透与一致性」
```

| 注解 | 是否执行方法 | 缓存动作 | 正确用法 |
| --- | --- | --- | --- |
| `@Cacheable` | 命中则**不执行** | 未命中执行后写入 | 查询方法 |
| `@CachePut` | **总是执行** | 用返回值覆盖 | 明确知道新值且要立刻可读 |
| `@CacheEvict` | 总是执行 | 删除条目（`allEntries=true` 清空） | **更新/删除后让缓存失效** |

纪律：**变更优先 `@CacheEvict`，不要用 `@CachePut` 猜值**。写库成功而写缓存失败、或并发交错时，`@CachePut` 会把陈旧快照塞进缓存且 TTL 内不会被纠正；`@CacheEvict` 最坏只是「下次读回源」，代价可控。

### 穿透与一致性：本地缓存的边界

`loadSlowly` 查不到就抛 `BusinessException`，配合不缓存 null，意味着**不存在的 id 每次都真实执行慢查询**（实测每次 ~805ms）。这是取舍：缓存 null 能挡穿透，但缓存里出现空值后 `get()` 返回 null 与「未命中」语义混淆。三种解法：

1. **接口层参数校验**（最便宜）：id 必须为正/在合法区间，非法直接 400，不进 service；
2. **短 TTL 的哨兵对象**：用占位对象代替 null（TTL 比正常数据短，如 30s），并用独立 cacheName 隔离；
3. **布隆过滤器**：合法 key 预加载，请求先过过滤器；**有假阳性但不漏**，新增 key 必须同步更新。是否可接受取决于**恶意 id 的请求占比**——接口对外且 id 可枚举时，方案 1 是必做项。

一致性方面，Caffeine **每个 JVM 各有一份**：实例 A `@CacheEvict` 只清了 A，实例 B 仍持旧值直到 TTL 到期，**TTL 就是业务能容忍的不一致时长**。常见防护：**击穿**（热点 key 过期瞬间大量回源）→ `@Cacheable(sync = true)` 或单飞互斥重建；**雪崩**（大批 key 同时过期）→ TTL 加随机抖动。需要「一处更新、处处生效」时必须上失效广播（Redis pub/sub、MQ）或换 Redis 集中式缓存——这是架构选择，不是注解参数能解决的。

### 自调用让缓存失效（与事务失效同源）

`loadWithoutCacheBySelfInvocation()` 内部直接 `this.loadSlowly(id)`，**不经过代理**，`@Cacheable` 完全不生效：

```
第一次 cost=0.808214s        第二次 cost=0.807159s        两次都 ~0.808s
loadCount: 1 → 2 → 3 …       每次都 +1，从未命中
```

对比正常调用（同一个 `ProductService`）：第一次 `costMillis=835`、`loadCount=1`；第二次 `costMillis=1`、`loadCount` **仍是 1**。同一份代码，代理决定生死；原因与 `@Transactional` 自调用失效完全一致——注解写在「真实对象内部」的调用上，代理看不到。

| 修法 | 写法 | 评价 |
| --- | --- | --- |
| 拆 Bean | 带注解的方法挪到另一个 `@Service` | **推荐**，无额外依赖 |
| 注入自身 | `@Autowired @Lazy private XxxService self;` → `self.method()` | 可行，但引入自我循环依赖 |
| `AopContext` | `((XxxService) AopContext.currentProxy()).method()` | 需 `exposeProxy=true`，强耦合 Spring API |

同一规律适用于 `@Async`、`@Retryable` 等一切代理驱动的注解。

### @Async：线程池必须自己定义

`@Async` 默认落到 `SimpleAsyncTaskExecutor`——它**不是线程池**，每次调用新建线程且不复用，高并发下线程数无上限。`AsyncConfig` 的关键配置（队列容量、拒绝策略、停机等待都必须显式设置）：

```java
executor.setCorePoolSize(4);  executor.setMaxPoolSize(8);  executor.setQueueCapacity(100);
executor.setThreadNamePrefix("basics-async-");   executor.setKeepAliveSeconds(60);
executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
executor.setWaitForTasksToCompleteOnShutdown(true);  executor.setAwaitTerminationSeconds(20);
```

- **执行顺序**：核心线程 → 队列 → 扩容到 max → 拒绝策略。队列设成 `Integer.MAX_VALUE` 时 `maxPoolSize` 永不生效（排不到扩容），池退化成「单线程 + 无限缓冲」；
- **`CallerRunsPolicy` 的背压**：队列满时由**提交任务的线程**自己执行，吞吐自动降到调用方速度，**天然限流且不丢任务**；代价是 Tomcat 工作线程被占住、响应变慢（相对的 `AbortPolicy` 丢任务，但快速暴露容量不足）；
- **线程命名不是洁癖**：`/actuator/threaddump` 里能直接筛出 `basics-async-1..4`；
- **`AsyncUncaughtExceptionHandler` 是必须项**：`void` 异步方法抛异常**不会**回到调用方，没 handler 就静默丢失（实测：`ERROR [basics-async-3] c.w.s.basics.config.AsyncConfig - 异步任务执行失败：method=fireAndForget, 参数个数=1`）；
- **返回值只允许 `void` 或 `Future` 家族**：`CompletableFuture` 才能让调用方编排；返回普通对象会被当同步处理，拿不到结果也不报错；`this.work()` 自调用同样失效。

实测 `GET /api/async/compare?tasks=5&sleepMillis=300`（**并行不是 300ms 而是 610ms**：核心线程 4 个，5 个任务必然有 1 个排在第二批——**并发度 = 核心线程数**，这是容量评估的依据）：

```
syncCostMillis = 1523     asyncCostMillis = 610     executedTotal = 5
task-1 on basics-async-1 (303ms)   task-2 on basics-async-2 (303ms)
task-3 on basics-async-3 (305ms)   task-4 on basics-async-4 (305ms)
task-5 on basics-async-1 (305ms)   ← 第 5 个复用了已空闲的 1 号线程
```

### @Scheduled：触发方式与调度线程池

| 写法 | 计时起点 | 任务超时的行为 |
| --- | --- | --- |
| `fixedRate = 10_000` | 上一次**开始**后 10s | 到点即触发新一次（可能并发/堆积） |
| `fixedDelay = 10_000` | 上一次**结束**后 10s | 天然串行，不堆积 |
| `cron = "0/30 * * * * ?"` | 日历时间 | 同 fixedRate，瞬时触发 |

本模块用 `fixedRate = 10_000, initialDelay = 5_000` 与 `cron = "0/30 * * * * ?"`。

- **cron 是 6 段**：`秒 分 时 日 月 周`，比 Linux crontab 多一个**秒**位，照抄 crontab 会错位；**`?` 表示「不指定」**，只能出现在日/周之一（两者都写 `*` 会歧义：「每月 1 号且每周一」）；
- **默认调度线程池只有 1 个线程**：多个 `@Scheduled` 互相阻塞，一个任务跑 5 分钟其他全部延后。本模块显式配 `spring.task.scheduling.pool.size: 2` + `thread-name-prefix: basics-sched-`，实测 `threaddump` 中 `basics-sched-1/2` 同时存在；
- **集群下每个实例都会执行**：`@Scheduled` 无协调机制，3 副本就是 3 倍执行，生产用**分布式任务调度**（xxl-job、ElasticJob、Quartz 集群）做选主分片，本节点到为止；**任务逻辑还必须幂等**（被重复/补偿触发是常态，优先 `UPDATE ... WHERE status='待处理'` 这类状态机写法）。

**①② 缓存命中 vs 自调用**（第二个 URL 多一段 `/self-invocation`）


## 思考点

- 你的业务能容忍多长时间的脏读？答不上来，`expireAfterWrite` 就只能靠猜——本地缓存的 TTL 就是一致性上限。
- 队列容量与 `maxPoolSize` 怎么配？`Integer.MAX_VALUE` 的队列会让 `maxPoolSize` 永不生效，这个池实际退化成了什么？
- `CallerRunsPolicy` 意味着 Tomcat 线程要去干异步的活。什么场景下这比丢任务更好？什么场景应该直接 `AbortPolicy` 快速失败？
- 定时任务从单机搬到 3 副本，同一时刻会有 3 个实例扫同一批数据。先做幂等改造还是先上 xxl-job？两者的失败模式有何不同？
- `@Cacheable` + `@Transactional` 写在同一个方法上时谁先执行？缓存命中时事务还会开吗？（提示：切面 order 可配）
