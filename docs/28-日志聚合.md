# 28 · 日志聚合（结构化日志 → 采集管道 → 查询）

> 模块：`springboot-basics/`（18010，`logback-spring.xml` + MDC traceId）+ 本机实测的一条极简采集管道。
> 实测环境：macOS、**无 Docker**、Boot 2.7.18；实例 18011（prod profile，文件日志）、
> 收集端 127.0.0.1:19280。本文所有输出均为实跑结果。

## 学什么

日志是三种可观测数据里最贵、也最不可替代的一种：指标告诉你「错误率 5%」，日志才告诉你
「是哪个用户、哪个参数、哪条 SQL」。但「把日志打进文件」离「能查」还有三段路：

```
应用写日志 → ① 落盘/标准输出（logback，带 traceId）
          → ② 结构化（解析成字段：谁、何时、哪条链路、哪个接口、多慢）
          → ③ 采集与聚合（采集端 → 缓冲 → 存储 → 查询/告警）
```

本篇用仓库现成的 `logback-spring.xml`（`docs/10` 的 `TraceIdFilter` 往 MDC 写 `traceId`）当源头，在一台
**没有 Docker** 的机器上把三段路走通：文件轮转、字段解析、脱敏、用 traceId 串起一次请求并做聚合统计。

## 核心代码

### 1. 日志格式：字段是设计出来的，不是打印出来的（`springboot-basics/src/main/resources/logback-spring.xml`）

```xml
<property name="FILE_PATTERN"
          value="%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%thread] [%X{traceId:-no-trace}] %logger{36} - %msg%n"/>
<!-- dev：只打控制台；prod：控制台 + 滚动文件 -->
<appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
    <file>logs/springboot-basics.log</file>
    <rollingPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
        <fileNamePattern>logs/springboot-basics.%d{yyyy-MM-dd}.%i.log</fileNamePattern>
        <maxFileSize>10MB</maxFileSize>        <!-- 单文件上限：到了就归档 -->
        <maxHistory>7</maxHistory>             <!-- 只留 7 天 -->
        <totalSizeCap>500MB</totalSizeCap>     <!-- 全目录硬顶：磁盘保护最后一道闸 -->
    </rollingPolicy>
</appender>
```

这 7 个字段（时间/级别/线程/traceId/logger/消息）是刻意排的：**能用固定分隔符切的，才谈得上被采集**。
`%X{traceId:-no-trace}` 里的 `:-no-trace` 表示 MDC 里没有值时的兜底，避免出现 `[]` 这种空字段。

### 2. 一行日志 → 一个 JSON 事件

原始行（prod 文件日志，真实内容）：

```
2026-10-08 15:37:58.746 WARN  [http-nio-18011-exec-7] [f3f41d9f75f24d7f] c.w.s.basics.web.AuthInterceptor - 鉴权失败：uri=/api/users, 期望请求头 X-Token（演示用 token 见配置 basics.security-token）
```

采集端按 `FILE_PATTERN` 定义的顺序解析、补上环境字段后，落成一行 JSON：

```json
{"ts":"2026-10-08 15:43:03.704","level":"DEBUG","thread":"http-nio-18011-exec-8","traceId":"a6a8aaece6f34ff4",
 "logger":"c.w.s.b.basics.web.AuthInterceptor","message":"请求完成：GET /api/users/9999 -> 404 (1 ms)",
 "uri":"/api/users/9999","uri_template":"/api/users/{id}","http_status":404,"duration_ms":1,
 "service":"springboot-basics","env":"prod","host":"...","file":"springboot-basics.log","offset":8241793}
```

字段设计的三条规矩：**环境字段（service/env/host）由采集端补**，应用不该关心；
**能变成数值的就别留字符串**（`duration_ms`、`http_status` 可直接做聚合与排序）；
**路径要模板化**（`uri_template`），否则「按 uri 聚合」会退化成按请求 ID 聚合——
这就是 `docs/27` 里标签基数陷阱的日志版本。

### 3. 采集端与收集端（本机实测的 Filebeat / 收集服务替身）

采集端的关键就三段：解析、轮转感知、批量投递（下面是实跑脚本的骨架，与后文输出一一对应）：

```python
LINE = re.compile(r"^(?P<ts>\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2}\.\d{3})\s+(?P<level>[A-Z]+)\s+\[(?P<thread>[^\]]+)\]"
                  r"\s+\[(?P<traceId>[^\]]+)\]\s+(?P<logger>\S+)\s+-\s+(?P<message>.*)$")
ACCESS = re.compile(r"(?P<method>GET|POST) (?P<path>\S+) -> (?P<status>\d{3}) \((?P<ms>\d+) ms\)")
SECRETS = [(re.compile(r"(?i)\b(bearer)\s+[A-Za-z0-9._\-]+"), r"\1 ***"),
           (re.compile(r"(?i)\b(x-token|token|authorization|password|secret)\b\s*[=:]\s*\S+"), r"\1=***"),
           (re.compile(r"(?<!\d)1[3-9]\d{9}(?!\d)"), "1**********")]

st = os.stat(LOG)
if ino is not None and (st.st_ino != ino or st.st_size < offset):   # 轮转感知：inode 变了或文件变小
    print("[rotate] 检测到文件轮转：inode %s -> %s" % (ino, st.st_ino), flush=True)
    fh.close(); fh, offset, ino = None, 0, None
```

收集端更简单：`POST /logs` 收一批 JSON 事件、按 JSON Lines 追加落盘。**契约只有一条：一批事件、一个
JSON 数组、失败整批重试**——换成 Filebeat/Fluent Bit 时变的只是这个进程，两端契约不变。

## 关键机制

**1. 结构化放在应用内还是采集端？** 应用内输出 JSON（`logstash-logback-encoder`，或 Boot 3.4+ 的原生
structured logging）字段最准、解析零成本，但要改代码/加依赖；采集端解析文本**零侵入**，代价是正则一改
就全乱。本模块走第二条路（不改 java 源码），实测 39,799 行解析失败 0 行（堆栈行被合并进上一条事件）。

**2. traceId 是日志与追踪唯一的缝合线。** `TraceIdFilter` 在请求进来时
`MDC.put("traceId", ...)`、请求结束时 `MDC.remove(...)`，所以同一次请求的所有日志都带同一个号；
`%X{}` 只读**当前线程**的 MDC，因此 `@Async`/线程池里必须手工传递（`docs/10` 的异步章节有例子），
跨服务则靠 HTTP 头（Sleuth 自动注入）。有了它，一次报错可以三步收敛：
指标发现异常 → Zipkin 里用 traceId 看到慢在哪一跳 → 日志里用同一个 traceId 看到具体参数。

**3. 采集架构的取舍**（本仓库这类教学环境与生产环境的差别就在这张表）：

| 方案 | 优点 | 代价 | 适用 |
| --- | --- | --- | --- |
| 应用直写 ES/Loki | 链路短、无本地文件 | 应用耦合存储、网络抖动丢日志、背压进业务线程 | 小规模、托管服务 |
| Filebeat/Fluent Bit 读文件 | 零侵入、可缓冲重试、`multiline`/`decode_json_fields` 现成 | 每台机多一个进程、要管 offset | 绝大多数场景 |
| `DaemonSet` 采集所有容器 stdout | 应用只管打印、平台统一 | 需统一日志格式、宿主机压力集中 | K8s 常规做法 |

存储侧：**Elasticsearch 全文检索强、成本高**（倒排索引 + 副本），适合「按关键字捞」；
**Loki 只索引标签、正文压缩存对象存储**，成本低一个量级，适合「先按 service/traceId 缩小范围再 grep」。
选型标准不是谁先进，而是「你 90% 的查询是关键字检索，还是标签 + 时间范围」。

**4. 级别与采样：级别是开关，不是过滤。** `logging.level.root=warn` 只是不输出，但 `log.debug` 里拼字符串
在热路径上照样有成本。生产建议：错误与关键业务事件全留、高频成功路径按比例采样（或只留慢请求）、DEBUG
按需开——本模块用 Actuator 的 `loggers` 端点运行时改级别（`POST /actuator/loggers/{name}`），不用重启。

**5. 脱敏要按「最坏样本」验证。** 本篇第一版规则只写了 `token|password|authorization` 的键值对，
实测 `Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJ1c2VyIn0.sig` 时**只吃掉了 `Bearer`，
JWT 本体原样落库**——见「动手验证 ⑦」。最终规则把 `Bearer\s+\S+` 单独列在前面，才真正脱干净。
结论：脱敏规则必须拿真实形态的样本回放，且优先用**字段白名单**（只输出已知安全字段），
而不是指望黑名单穷举。

**6. 轮转与磁盘保护是两件事。** `maxFileSize` + `maxHistory` + `totalSizeCap` 控制「应用侧留多少」
（实测 5 个 10MB 归档 + 活动文件 = 62MB）；采集端还要处理「文件被换掉」：`inode` 变化或文件变小
就必须从 0 重读，否则日志会静默停采。反过来也要防重：采集端重启后若从 0 重读整文件，
就会重复投递——真实采集器用 offset 文件（Filebeat 的 registry）解决，本脚本用内存 offset，
重启会重读，属于「至少一次」投递。

**7. 多行是日志采集的头号麻烦。** Java 堆栈一行一个 `at ...`，不合并就是几十条无意义事件；本脚本用
「行首不是时间戳就并入上一条」的规则（等价 Filebeat 的 `multiline.pattern`），代价是 `message` 要能存换行。

## 思考点

1. 应用直写日志系统 vs 写文件后由采集器搬运：网络抖动、存储不可用、背压这三种情况分别会怎样表现？
   哪个方案更容易把日志丢失变成「业务故障」？
2. `traceId` 只放在 MDC 里，`@Async`、定时任务、Kafka 消费线程里为什么拿不到？跨服务传递时，
   哪些环节是框架自动做的、哪些必须自己塞进 HTTP 头或消息头？
3. 脱敏用黑名单（正则替换敏感词）还是白名单（只输出已知字段）？本文第一版漏掉 JWT 本体的例子
   说明了黑名单的什么问题？如果日志要落盘 7 天并给第三方查询，你会怎么设计更强的一道闸？
4. `maxFileSize=10MB`、`maxHistory=7`、`totalSizeCap=500MB` 三个参数分别在防什么？
   如果采集端挂了 3 天、应用日志照写，最先出问题的是哪一环？
5. 采集端重启后 offset 丢失会重复投递（至少一次），如何让下游「去重」？
   如果业务方要求日志「一条不丢且不重」，成本会落在哪一层？
