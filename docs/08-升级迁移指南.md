# Spring Cloud 升级迁移指南：Edgware.SR5 → 2021.0.9 → 2025.1.3

> 本文记录本项目**两次**大版本升级的全部实际改动，每一条都对应仓库里的真实提交，
> 可直接当作同类项目的迁移核对清单使用：
>
> - **第一部分**：`Spring Boot 1.5.2 + Spring Cloud Edgware.SR5` → `Spring Boot 2.7.18 + Spring Cloud 2021.0.9`（Java 8）；
> - **第二部分**：`Boot 2.7.18 + Cloud 2021.0.9` → **`Spring Boot 4.0.8 + Spring Cloud 2025.1.3 + SCA 2025.1.0.0`（Java 17）**，
>   含 Nacos 3.x / Sentinel 1.8.9 / Seata 2.5.0（Apache 版）等新组件栈在 2025.1 下的变化。
>
> 旧版实现只保留在本仓库历史提交中；每部分的结论都以"本机实测跑通"为准，不做纯文档推演。

## 1. 升级路径选择

| 路线 | 组合 | 组件变化 | 适用 |
| --- | --- | --- | --- |
| 第一部分采用 | Boot 2.7.18 + Cloud 2021.0.9 + Java 8 | Zuul→Gateway、Ribbon→LoadBalancer、Hystrix→Resilience4j | 改动适中、保住 Java 8 |
| 更彻底 | Boot 3.x + Cloud 2023.x + Java 17 | 同上 + javax→jakarta、全部配置属性重校验 | 新项目/已上 Java 17 |
| **第二部分实际走的路（见 §10 起）** | **Boot 4.0.8 + Cloud 2025.1.3 + SCA 2025.1.0.0 + Java 17** | 上面两种的并集，再加 Jackson 3、tracing 模型换代、Nacos 3.x | 想一次到位、有人力做全量冒烟 |

> 第一部分当时没直接选 Boot 3：官方要求 Java 17 与 javax→jakarta 命名空间迁移，
> 对纯教学 demo 收益有限、噪音大；2.7.18 是 2.x 最终版，与 3.x 的"组件形态"已一致。
> 后来第二部分一次到位升到 Boot 4，验证了当时的判断：**javax→jakarta 这一步只做一次**，
> 真正的成本在运行时行为（Eureka 开关、tracing 模型、配置前缀）而不是改名本身。

## 3. Netflix 组件退役：starter 更名与替代实现（本次升级核心）

Spring Cloud 2020.0（Ilford）起，Netflix 家族除 Eureka 外全部移出，官方给出替代矩阵：

| 能力 | Edgware 旧组件 | 2021.0 新组件 | 业务代码是否要改 |
| --- | --- | --- | --- |
| 注册中心客户端 | `spring-cloud-starter-eureka` | `spring-cloud-starter-netflix-eureka-client` | 否 |
| 注册中心服务端 | `spring-cloud-starter-eureka-server` | `spring-cloud-starter-netflix-eureka-server` | 否 |
| 客户端负载均衡 | Ribbon（`spring-cloud-starter-ribbon`） | Spring Cloud LoadBalancer（`spring-cloud-starter-loadbalancer`） | **否**：`@LoadBalanced RestTemplate` 语义不变 |
| 声明式调用 | Feign（`spring-cloud-starter-feign`） | OpenFeign（`spring-cloud-starter-openfeign`） | 仅 import 包名：`netflix.feign` → `openfeign` |
| 熔断降级 | Hystrix（`@HystrixCommand`） | Spring Cloud CircuitBreaker + Resilience4j | **是**：注解改为 `CircuitBreakerFactory.run()`，见 §3.2 |
| 服务网关 | Zuul（`@EnableZuulProxy`） | Spring Cloud Gateway（WebFlux） | **是**：路由配置整体迁移，见 §3.3 |
| Hystrix 看板 | `@EnableHystrixDashboard` | Actuator 端点 `/actuator/circuitbreakers`、`/actuator/circuitbreakerevents` | 概念替代 |
| 服务追踪 | Sleuth 1.x + 自建 zipkin-server 模块 | Sleuth 3.1 + 官方独立 Zipkin（非 Boot 库） | 配置迁移，见 §5 |

### 3.1 Ribbon → Spring Cloud LoadBalancer

最省心的一处：本项目消费端统一使用 `@LoadBalanced RestTemplate` 以 `http://服务名/...` 方式调用，
该抽象在 LoadBalancer 下**语义与代码完全不变**，只需：

1. 删除 `spring-cloud-starter-ribbon`，新增 `spring-cloud-starter-loadbalancer`；
2. （注意）`eureka.client.healthcheck.enabled` 依赖 actuator，保持原样即可。

> 踩坑提醒：若只换 eureka client 不加 loadbalancer，启动时 `@LoadBalanced` 调用会报
> `No Feign Client for loadBalancing` / 无可用实例类错误——LoadBalancer 不再随 eureka client 自动带入。

### 3.2 Hystrix → Resilience4j（Spring Cloud CircuitBreaker）

旧写法（Edgware 版 `HystrixServiceImpl`）：

```java
@HystrixCommand(fallbackMethod = "fallback")
public String testHystrix() {
    return restTemplate.getForObject("http://service-producer/testHystrix", String.class);
}
public String fallback() { ... }
```

新写法（develop 分支同名文件）：

```java
@Autowired
Resilience4JCircuitBreakerFactory circuitBreakerFactory;

public String testHystrix() {
    return circuitBreakerFactory.create("testHystrix").run(
            () -> restTemplate.getForObject("http://service-producer/testHystrix", String.class),
            this::fallback);   // fallback 签名建议携带触发异常：fallback(Throwable t)
}
```

语义对照：

| Hystrix | Resilience4j |
| --- | --- |
| 默认隔离线程池 | 默认信号量（demo 无需改） |
| `hystrix.command.default.execution.isolation.thread.timeoutInMilliseconds` | `resilience4j.timelimiter.configs.default.timeout-duration` |
| 熔断窗口/阈值 | `resilience4j.circuitbreaker.configs.default.sliding-window-*` / `failure-rate-threshold` |
| 打开后恢复探测 | `wait-duration-in-open-state`（半开自动进入） |
| Hystrix Dashboard | `management.endpoints.web.exposure.include: "*"` 后访问 `/actuator/circuitbreakers` |

### 3.3 Zuul → Spring Cloud Gateway

三个最容易踩的坑：

1. **WebFlux 冲突**：Gateway 基于 WebFlux，模块里绝不能再引入 `spring-boot-starter-web`，否则启动直接失败
   （`Spring MVC found on classpath, which is incompatible with Spring Cloud Gateway`）；
2. **配置前缀整体迁移**：`zuul.routes.*` → `spring.cloud.gateway.routes.*`；Zuul 默认按服务名转发，
   Gateway 显式等价做法是开启 `spring.cloud.gateway.discovery.locator.enabled=true`
   （自动生成 `/<服务名>/**` 路由，建议配 `lower-case-service-id: true`）；
3. **注解消失**：`@EnableZuulProxy` 直接删除，Gateway 无需开启注解；`@SpringCloudApplication`（内含 Hystrix）也已移除。

新路由示例（见 `zuul/src/main/resources/application.yml`）：

```yaml
spring:
  cloud:
    gateway:
      discovery:
        locator:
          enabled: true          # /service-producer/** 自动路由
          lower-case-service-id: true
      routes:
        - id: service-producer
          uri: lb://service-producer   # lb:// = 从注册中心负载均衡
          predicates:
            - Path=/api/producer/**
          filters:
            - StripPrefix=2            # 剥掉 /api/producer 两段再转发（StripPrefix 按"段"计数）
```

## 4. 配置体系变化（每个模块都受影响）

### 4.1 bootstrap.yml 不再默认生效（Boot 2.4 起）

Spring Cloud 2020.0 起禁用了 bootstrap 上下文，需要引入：

```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-bootstrap</artifactId>
</dependency>
```

本项目选择**保留 bootstrap.yml 的教学形态**（config-first 模式更直观），因此各业务模块统一补了该依赖。

### 4.2 Sleuth 配置键更名

```yaml
spring:
  sleuth:
    sampler:
      percentage: 1        # 旧
      probability: 1.0     # 新（同义更名，旧键已无效）
```

### 4.3 Actuator 安全模型重构

| 旧（1.5） | 新（2.x） |
| --- | --- |
| `management.security.enabled: false` 关闭安全拦截 | 已废除；2.x 端点默认只暴露 health/info，需显式放开 |
| `management.endpoints.web.exposure.include` 不存在 | `include: "*"` 放开全部端点 |

### 4.4 Flyway 5 → 8.5

1. 配置前缀 `flyway.*` → `spring.flyway.*`（Boot 2.x 托管）；
2. `flyway: locations: /schema` → `locations: classpath:/schema`；
3. **Flyway 8.2 起 MySQL 方言拆分到独立包**，必须新增 `org.flywaydb:flyway-mysql`，否则报
   `Unsupported Database: MySQL 8.0`；
4. Flyway 8.5 支持到 MySQL 8.x；比 8 更新的 MySQL 版本（如本机 Homebrew 的 26.x）会报
   不支持的数据库版本，教学环境请用 MySQL 8.0（docker-compose 已固定）。

## 5. 服务追踪：Sleuth 3.1 + 官方独立 Zipkin

Zipkin 2.14 起**不再提供 Spring Boot starter/库形态**（`io.zipkin.java:zipkin-server` 已成为历史产物），
本项目 zipkin 自建模块随之删除，改为官方独立发行版：

- 本地快速启动：`docker compose up -d`（docker-compose.yml 已内置 openzipkin/zipkin:3，端口 9411）；
- 无 Docker 环境：从 Maven Central 下载 `io.zipkin/zipkin-server/<版本>/zipkin-server-<版本>-exec.jar`
  后 `java -jar zipkin-server-*-exec.jar`；
- 业务模块只保留 `spring-cloud-starter-sleuth` + `spring-cloud-sleuth-zipkin` 两个依赖，零代码改动；
- 报文默认仍是 HTTP POST 到 `spring.zipkin.base-url`（新版也可换 Kafka/RabbitMQ 传输，教学未展开）。

## 6. Java 语言与启动写法

| 旧 | 新 | 备注 |
| --- | --- | --- |
| `new SpringApplicationBuilder(X.class).web(true).run(args)` | `SpringApplication.run(X.class, args)` | `web(true)` 已废弃，2.x 默认即 SERVLET 应用 |
| `org.apache.log4j.Logger` | `org.slf4j.Logger` + Logback | log4j 1.x EOL 且 Boot 2.x 默认日志栈为 slf4j+Logback |
| 非 static 内部类 `@Configuration` | `static class` | Boot 2.x 对非静态内部配置类打警告（防止外部类实例泄漏） |
| `@RequestBody` 出现在 Service 接口实现上 | 移除（属 MVC 注解误用） | 语义无影响，纯清理 |
| 测试 `@RunWith(SpringRunner.class)` | 直接标注 `@SpringBootTest` | JUnit 5 无需 Runner |

## 7. 非升级但必要的工程修正

1. **资源目录规范化**：原仓库所有模块的配置文件放在非标准的 `<模块>/resources/`（Maven 打不进 jar，
   过去只能在 IDE 里运行），已全部 `git mv` 到 `src/main/resources/`；
2. **URL 硬编码修正**：consumer/feign 上传文件路径 `D:\tempFile`（Windows 专属）改为
   `System.getProperty("java.io.tmpdir")` 跨平台临时目录；
3. **`e.printStackTrace()` 清理**：统一改为 slf4j `logger.error(..., e)`；
4. **`@Value("${name}")` 加默认值**：`${name:unknown}`，避免脱离配置中心时启动失败，便于最小化验证；
5. **网关模块包名**：`com.wkedong.springcloud.zuul` → `com.wkedong.springcloud.gateway`
   （模块目录名沿用 `zuul` 历史名，避免破坏既有路径与外部引用）。

## 11. 编译期就会拦下你的改名（Boot 4 模块拆分）

Boot 4 把原来的"一个大 `spring-boot` 包"拆成了很多小模块，很多常用类**换了包、也换了构件**：

| 旧 | 新 | 影响面 |
| --- | --- | --- |
| `spring-boot-starter-aop` | **`spring-boot-starter-aspectj`** | AOP 相关模块的 pom |
| `org.springframework.boot.web.client.RestTemplateBuilder` | **`org.springframework.boot.restclient.RestTemplateBuilder`**，且在独立模块 **`spring-boot-restclient`** | `spring-boot-starter-web` **不再**传递它（本仓库改为直接给 `RestTemplate` 挂 `ObservationRegistry`，见 §14.3） |
| `org.springframework.boot.test.autoconfigure.web.servlet.WebMvcTest` | **`org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest`**，需要显式依赖 **`spring-boot-webmvc-test`** | 测试切片**不会**被 `spring-boot-starter-test` 带进来，漏了就是 `package does not exist` |
| `@MockBean` / `@SpyBean` | **`@MockitoBean` / `@MockitoSpyBean`**（`org.springframework.test.context.bean.override.mockito`） | 所有用 `@MockBean` 的测试 |
| `org.springframework.boot.actuate.health.{HealthIndicator,Health,Status}` | **`org.springframework.boot.health.contributor.*`**（模块 `spring-boot-health`） | 自定义健康检查 |
| `org.springframework.boot.web.context.WebServerInitializedEvent` | **`org.springframework.boot.web.server.context.WebServerInitializedEvent`** | 取真实端口的监听器 |
| `com.fasterxml.jackson.databind.ObjectMapper` | **`tools.jackson.databind.ObjectMapper` / `JsonMapper`** | 手写 JSON 的地方；`JacksonException` 变成非受检异常 |

另外两个不体现在编译期、但会浪费半天的点：

1. **Jackson 2 从依赖树里消失了**。Boot 4 只带 Jackson 3，仍在用 `com.fasterxml.jackson.*` 的三方库
   （本次踩到的是 Seata）会运行时报 `NoClassDefFoundError`。解决方式见 §16.4。
2. **改完依赖必须 `mvn clean package`**。Boot 4 的 `repackage` 在 jar 未变化时会复用旧的嵌套依赖，
   只跑 `mvn package` 会出现"依赖明明加上了、`BOOT-INF/lib` 里却没有"的诡异现象（本机实测踩到）。

## 12. 配置体系的第二次迁移：bootstrap 彻底退场

第一部分已经讲过 `bootstrap.yml` 在 Boot 2.4 起不再默认生效；这次是**彻底移除**：

```yaml
# 旧（2021.0.x）：bootstrap.yml + spring-cloud-starter-bootstrap
spring:
  application:
    name: service-consumer-feign
  cloud:
    config:
      uri: http://localhost:6010/
      label: develop
      profile: dev
```

```yaml
# 新（2025.1.x）：全部搬进 application.yml，用 Config Data 的 import 声明
spring:
  config:
    # optional: 前缀 = 配置中心没起来也能启动（本地开发/教学常用）
    import: optional:configserver:http://localhost:6010/
  cloud:
    config:
      label: develop
      profile: dev
      name: service-consumer-feign
```

仓库里 7 个模块的 `bootstrap.yml` 被 `git mv` 成 `application.yml`（保留历史），
并把 Sleuth 时代的 `spring.zipkin.*` 一并搬到 `management.zipkin.tracing.*` 之下。

## 13. 运行时陷阱一：Eureka 客户端（Netflix 5.0.2）

两个开关必须显式关掉，否则**启动失败或端点 500**，而且错误信息完全不指向配置：

### 13.1 `eureka.client.jersey.enabled: false`

Netflix 5.0.2 移除了 Jersey 传输相关的配置 Bean，但 `eureka.client.jersey.enabled` 的判断是
`matchIfMissing = true`（默认仍然开着），于是容器里造不出 `eurekaClient`：

```
No qualifying bean of type
'com.netflix.discovery.shared.transport.jersey.TransportClientFactories' available
```

`TransportClientFactories` 是 Jersey 传输的专属接口，而现在实际走的是 `RestClient` 传输——
显式关掉这个开关后，Eureka 客户端才回到正常实现。**7 个 Eureka 客户端模块全部要加。**

### 13.2 `eureka.client.refresh.enable: false`

默认的 Eureka 客户端 Bean 是 refresh scope 的。当 `/actuator/health`（健康检查会碰 Eureka 状态）
或 `POST /actuator/refresh` 触发 refresh scope 重建时，重建过程抛 NPE：

```
DiscoveryClient : Fetch registry error at startup: null
BeanCreationException: ... Factory method 'eurekaClient' threw exception with message: java.lang.NullPointerException
```

表现就是 **`/actuator/health` 和 `/actuator/refresh` 双双 500**（业务接口却完全正常，极具迷惑性）。
关掉 refresh scope 后走普通单例客户端，两个端点立刻恢复 200（实测 `refresh` 返回 `[]`）。

## 14. 运行时陷阱二：链路追踪（Sleuth 退场后的三件必做事）

第一部分的 Sleuth 是"自动装饰一切"的模型；Micrometer Tracing 是"观测驱动"的模型——
**没有观测注册表就没有 traceId**。这次踩到的三件事缺一不可：

### 14.1 追踪自动配置要单独引：`spring-boot-starter-zipkin`

Boot 4 把 tracing 的自动配置从 actuator 里拆了出去。只把 Sleuth 依赖删掉、换成
`micrometer-tracing-bridge-brave` 是不够的，会直接启动失败：

```
No qualifying bean of type 'io.micrometer.tracing.Tracer' available
```

正确做法是引 `spring-boot-starter-zipkin`（它聚合了 tracing 自动配置 + Brave 桥 + Zipkin reporter）。

### 14.2 传播类型默认变成 W3C

Sleuth 时代下游能看到的头是 `X-B3-TraceId` / `X-B3-SpanId`；现在本机抓到的是：

```
traceparent: 00-6ac76387b3e878fd1a9571e703eba824-e3a2d548cd7452d6-01
```

如果下游服务或网关日志解析写死了 `X-B3-*`，链路会"看起来断掉"。要么统一改读 `traceparent`，
要么显式把 `management.tracing.propagation.type` 设回 `b3`。

### 14.3 Feign 与 RestTemplate 都要显式接上观测

这是本次最容易漏、症状最像"网络问题"的一条——**两边都静默丢 traceId**：

| 客户端 | 必须做的事 | 漏掉的后果 |
| --- | --- | --- |
| OpenFeign | 显式引 **`io.github.openfeign:feign-micrometer`**（`MicrometerObservationCapability` 在这个独立构件里，OpenFeign 核心不含） | 没有客户端 span、请求头里没有传播信息 |
| `RestTemplate` | 注入 `ObservationRegistry` 并 `restTemplate.setObservationRegistry(registry)`（或改用 Boot 的 `RestTemplateBuilder`，但 Boot 4 要额外引 `spring-boot-restclient`） | 同上 |

漏掉时的**唯一症状**：Zipkin 里上下游各自是一条独立 trace。当时 4 个消费者全部中招：

```
修复前：consumer trace 6ac761c60a581b4d1efc7da987cc977f
        producer trace 6ac761c6f60458ad676eb22fa0eb93de   ← 只有高 32 位相同（同一秒生成）
修复后：同一条 trace 下同时有 service-consumer-feign 与 service-producer 的 span
```

### 14.4 注解式 span 的开关

Sleuth 的 `@NewSpan` / `@SpanTag` 已不存在，改用 Micrometer 的 `@Observed`；
并且**必须**打开 `management.observations.annotations.enabled: true`，否则注解不生效、Zipkin 里什么都不出现。
本机实测开启后 Zipkin 里同时出现编程式 `producer-custom-span` 与注解式 `producer-annotated-span`。

## 15. 运行时陷阱三：Spring Cloud 2025.1 的默认值与前缀变化

### 15.1 Gateway：starter 与配置前缀双改

```xml
<!-- 旧 -->
<artifactId>spring-cloud-starter-gateway</artifactId>
<!-- 新（WebFlux 版；2025.1 起官方把它叫 gateway-server-webflux） -->
<artifactId>spring-cloud-starter-gateway-server-webflux</artifactId>
```

```yaml
# 旧
spring.cloud.gateway.routes[0]...
management.endpoint.gateway.enabled: true
# 新：整棵配置树挪到 server.webflux 之下；actuator 开关换成访问级别
spring.cloud.gateway.server.webflux.routes[0]...
management.endpoint.gateway.access: read-only
```

顺带一个命令级的坑：**服务发现路由（locator）用小写服务名**，`/service-producer/testGet` 通、
`/SERVICE-PRODUCER/testGet` 不通。

### 15.2 OpenFeign：配置前缀搬家（旧键静默失效）

```yaml
# 旧（在新版本里仍然"能解析"，但完全不生效）
feign:
  circuitbreaker.enabled: true
  client.config.default.readTimeout: 2000
# 新
spring:
  cloud:
    openfeign:
      circuitbreaker.enabled: true
      client.config.default.read-timeout: 2000
```

这是**最隐蔽的一类迁移问题：不报错、不警告、配置就是没用**。本机对照实验：

| 配置位置 | 请求 `producer /testSlow?seconds=5`（读超时设 2s） |
| --- | --- |
| 旧前缀 `feign.client.config.*` | 请求跑满 5 秒才返回，`costMillis≈5167`，**没有任何降级** |
| 新前缀 `spring.cloud.openfeign.client.config.*` | **约 3.0s 降级**（`costMillis≈3005`），`TimeoutException`，fallbackFactory 兜底 |

这里 3s 而不是 2s 的原因值得记住：`read-timeout: 2000` 触发的是 RetryableException，紧接着
客户端 `Retryer.Default(100ms, 1s, 3)` 开始重试，最后由 Resilience4j 的 **TimeLimiter 3s** 掐断——
三个数值叠起来才是总耗时；把 TimeLimiter 配得比 readTimeout 还小时，看到的就是「读超时还没到就被砍」。

注意 SCA 的 `feign.sentinel.enabled` **没有变**（2025.1.0.0 实测仍是这个键），
容易和 OpenFeign 自己的前缀混淆。

### 15.2.1 feign-form 换了 groupId：两套同名类会静默共存

OpenFeign 13.6.1 把 feign-form 收编进主仓库，**坐标的 groupId 变了**：

```xml
<!-- 旧：独立仓库，版本 3.8.0 -->
<dependency>
    <groupId>io.github.openfeign.form</groupId>
    <artifactId>feign-form-spring</artifactId>
    <version>3.8.0</version>
</dependency>
<!-- 新：并入 OpenFeign 主仓库，版本由 BOM 管理（13.6.1） -->
<dependency>
    <groupId>io.github.openfeign</groupId>
    <artifactId>feign-form-spring</artifactId>
</dependency>
```

因为 **groupId 不同，Maven 不会做版本仲裁**：旧依赖不删，两套 `feign.form.spring.SpringFormEncoder`
就会同时躺在 `BOOT-INF/lib` 里（本机实测 fat jar 里 3.8.0 与 13.6.1 并存），
最终加载到哪一份取决于 classpath 顺序——一个不报错、只在特定调用路径上偶发行为差异的隐患。
好在 13.6.1 的 `SpringFormEncoder` 仍是无参构造、仍原生支持 `MultipartFile`，
所以**删掉旧显式依赖即可，`new SpringFormEncoder()` 的代码一行都不用改**；
改完 `clean package` 后 fat jar 里只剩 13.6.1，`scripts/verify-core.sh` 复跑 44/44 通过（含 multipart 透传）。

### 15.3 构建与测试

- Surefire 3.x 里 `-DfailIfNoTests=false` 已改名，多模块下仍会因"某模块没有匹配的测试"失败，
  需要补 `-Dsurefire.failIfNoSpecifiedTests=false`：

  ```bash
  mvn -B -Dtest='*Test,*Tests' -DfailIfNoTests=false -Dsurefire.failIfNoSpecifiedTests=false test
  ```

- Framework 7 的缓存是 fail-fast 的：`@WebMvcTest` 切片里没有 `CacheManager` 会**启动失败**
  （不是跳过缓存），需要 `@Import(CacheConfig.class)` 之类把配置补齐。

## 16. 新组件栈在 2025.1 下的变化（Nacos / Sentinel / Stream / Security / Seata）

### 16.1 Nacos：客户端 3.1.1 必须配服务端 3.x

SCA 2025.1.0.0 把 nacos-client 升到 **3.1.1**，而 3.x 客户端里
`Constants.DEFAULT_NAMESPACE_ID` 由空串 `""` 变成了 **`"public"`**。
如果服务端还是 Nacos 2.x（默认命名空间 ID 是 `""`），**所有 `spring.config.import` 拉回来的配置都是空**：

```
NacosConfigDataLoader : [Nacos Config] config[dataId=nacos-demo.properties, group=DEFAULT_GROUP] is empty
```

注意它**不会报错**：配置订阅成功（日志里有 `add-listener ok`），只是内容为空，
应用照常启动、照常用本地默认值——非常适合排查半天。把服务端升到 3.2.4 之后：

```
NacosConfigDataLoader : [Nacos Config] Load config[dataId=nacos-demo.properties, group=DEFAULT_GROUP] success
```

Nacos 3.x 还有几处运维侧变化（教学环境要跟着改）：

| 项 | 2.x | 3.x |
| --- | --- | --- |
| 控制台端口 | 与 API 同端口（8848） | **独立 8080**（API 仍 8848、gRPC 9848） |
| 配置 API | `POST/GET /nacos/v1/cs/configs`、`/nacos/v2/cs/config` | **v1/v2 已移除（404）**；发布 `POST /nacos/v3/admin/cs/config`、读取 `GET /nacos/v3/client/cs/config` |
| 鉴权 | `nacos.core.auth.enabled` 一个开关 | 拆成 client/admin/console 三个开关，**admin/console 默认开启**（即使 `nacos.core.auth.enabled=false`，v3 admin API 仍会 `access denied / User not found`） |
| 服务端身份 | 可不配 | **必须**配 `nacos.core.auth.server.identity.key/value`，否则启动报 `errCode: 50002, Empty identity` |
| standalone 启动 | `java -jar target/nacos-server.jar` | 需带 `-Dloader.path=<目录>/plugins`（Derby 驱动在 plugins 目录里） |

`spring.config.import` 的优先级语义也顺带实测清楚了（与旧 bootstrap 时代的 `shared-configs` 不同）：

1. 导入的 Nacos 配置**优先于**导入它的本地 `application.yml`（同名 key 远端胜出）；
2. **多条 import 后写的赢**——`nacos-demo.properties` → `nacos-demo-dev.properties` → `nacos-demo-shared.properties`
   三条都定义 `nacos.demo.title` 时，最终生效的是最后一条（shared）；
3. 动态刷新不必重启：往 dataId 里新增 key，长轮询约 12 秒内就会进 Environment。

### 16.2 Sentinel：Web 适配器进入 v6x 包

```java
// 旧（Spring 5 时代）
com.alibaba.csp.sentinel.adapter.spring.webmvc.callback.BlockExceptionHandler
// 新（Jakarta / Spring 6+）
com.alibaba.csp.sentinel.adapter.spring.webmvc_v6x.callback.BlockExceptionHandler
// 方法签名也变成 4 参
handle(HttpServletRequest req, HttpServletResponse resp, String resourceName, BlockException ex)
```

实测：URL 资源规则（`/system/probe`，QPS=2）前 2 次 200、之后 **HTTP 429** 且响应体走自定义 handler；
`@SentinelResource` 的 blockHandler 路径返回 `code=7001`；慢调用比例熔断后 `/degrade/slow` 由 ~1s 变 ~2ms。

### 16.3 Stream / Kafka：`KafkaHeaders.MESSAGE_KEY` 改名

spring-kafka 4 把常量名去掉了 `MESSAGE_` 前缀：`KafkaHeaders.MESSAGE_KEY` → **`KafkaHeaders.KEY`**。
实测发送带 key 的消息，消费端 `kafka_receivedMessageKey=k-001`；毒消息重试 3 次（约 1s 间隔）
后进 DLQ，DLQ 消息头保留 `x-original-topic` / `x-original-partition` / `x-original-offset` / `x-original-timestamp`。

### 16.4 Seata 2.5.0：Apache 版 + 必须补 Jackson 2

- 主包名从 `io.seata.*` 变成 **`org.apache.seata.*`**（starter 坐标仍是 `spring-cloud-starter-alibaba-seata`）；
  **兼容包 `io.seata.*` 仍在**——实测 `seata-all-2.5.0.jar` 里两套都有（`org/apache/seata` 1564 项、`io/seata` 193 项），
  所以本仓库沿用 `io.seata.*` 的代码照样编译运行，新代码建议写 `org.apache.seata.*`；
- **必须补 Jackson 2**，否则运行时报：

```
NoClassDefFoundError: com/fasterxml/jackson/core/JsonProcessingException
```

  而它的**外在表现极具误导性**——下单直接失败，报的是：

```
Could not open JDBC Connection for transaction    （xid=null）
```

  看到这个错误第一反应是数据库/驱动/连接池问题，实际跟数据库毫无关系。补上
  `com.fasterxml.jackson.core:jackson-databind`（本次用 2.21.7；Boot 4 的 BOM 不再管理 Jackson 2，
  所以在根 pom 里用 `jackson2.version` 统一管理）后恢复正常。
  别忘了 §11 提到的 `mvn clean package`，否则新依赖进不了 fat jar。

实测 AT 事务（order 8250 + inventory 8260 + seata-server 8091）：

```
正常：{"orderId":13,...,"inventoryStock":91,"xid":"192.168.85.52:8091:5161956697001525281"}
异常：{"code":50000,"message":"演示用异常：订单 14 已写入、库存已扣减 5 件（余量 86），随后主动失败"}
      回滚后库存仍是 91，订单 14 不在 orders 表里
```

一个容易误用的证据：`undo_log` 在全局事务结束后会被 Seata 清空（实测两端 `count(*)=0`），
**不能**拿它当"回滚发生了"的依据，要看业务表数值。
