# 14 · 可观测与运维

> 模块：`springboot-basics/`（8010，H2 内存库，零外部依赖），启动见 [09-本地运行指南](09-本地运行指南.md)。
> 关联：[10-Web 层工程化](10-Web层工程化.md) 的 `TraceIdFilter` 提供 MDC 追踪号；[11-配置体系](11-配置体系.md) 的 `basics.*` 会出现在 `env`/`configprops` 里；下一篇 [15-自动配置与自定义 Starter](15-自动配置与自定义Starter.md) 拆 `AuditLogger` 的装配。
> 本文响应片段与停机/打包证据均为 8010 实测输出。

## 学什么

功能跑通只是第一步，上线后要靠**外部可观测的入口**排障，而不是「登机器看日志」。Actuator 把这套入口标准化了：`health` 给**探针**看（能不能接流量）、`info` 给**人**看（跑的是哪个版本/环境）、`metrics` 给**监控系统**看（数值指标）、`loggers`/`env`/自定义端点给**排障时的你**看（不重启就能定位）。核心矛盾是：**这些端点越有用，暴露面就越危险**——`env` 里有连接串、`configprops` 里有配置、`threaddump`/`heapdump` 里有内存中的业务数据。


## 核心代码
### Actuator 端点全景

本模块 `exposure.include` 打开了 12 个端点（实测 `/actuator` 索引共 20 个链接，含带路径参数的子链接）：

| 端点 | 回答什么问题 | 风险 |
| --- | --- | --- |
| `health` / `info` | 实例能不能服务、依赖是否正常 / 哪个版本、环境、负责人 | 低（`show-details=always` 会泄露内部组件名） |
| `metrics` / `loggers` | 请求量、延迟、连接池、缓存命中率 / 现在什么级别、能否临时调细 | 中～**高**：`loggers` 被改成 `TRACE` 可打爆日志盘 |
| `env` / `configprops` | 配置从哪来、最终值是什么；`@ConfigurationProperties` 绑成了什么 | **高**：连接串、密钥、内部地址（Spring 按 key 名脱敏，但那是启发式） |
| `beans` / `mappings` / `conditions` | 有哪些 Bean、有哪些 URL、自动配置为何生效/没生效 | 中：依赖地图 + 接口清单 + 类路径 |
| `caches` / `scheduledtasks` | 用了哪些缓存、能不能清 / 注册了哪些定时任务 | 中（`DELETE /actuator/caches/{name}` 会清线上缓存） |
| `threaddump` / `heapdump` / `shutdown` | 哪些线程卡住了 / 下载堆快照 / 远程关停 | **高～极高**：线程栈含 SQL 与参数值；后两者本模块未开启（实测索引中无此两项） |

暴露面控制分三层，`application.yml`（dev）与 `application-prod.yml`（prod）已示范前两层——dev 放开 12 个端点便于排查，prod 只留 `health,info,metrics,prometheus` 并把 `show-details` 收到 `when-authorized`：

```yaml
management.endpoints.web.exposure.include: health,info,metrics,beans,env,configprops,loggers,mappings,threaddump,caches,scheduledtasks,conditions,basics   # dev
management.endpoints.web.exposure.include: health,info,metrics,prometheus   # prod：只留必要
management.endpoint.health.show-details: when-authorized                    # prod：细节只在认证后可见
```

1. **`include` 白名单**：默认只暴露 `health`，要开就逐个点名，绝不写 `*`；prod 只留 `health,info,metrics`，需要 `env` 时临时开、用完关；
2. **物理与认证隔离**（生产必做）：`management.server.port=8081` 让管理端点走独立内网端口，安全组只放行运维网段；接入 Spring Security 后对 `/actuator/**` 单独鉴权，`show-details=when-authorized` 才真正走到「需认证」分支。

判断标准很简单：**这个端点泄露的信息，能不能帮攻击者找到下一个突破口**——`env`/`configprops`/`threaddump`/`heapdump` 的答案是「能」，所以默认不开。

### 自定义健康检查：HealthIndicator

`BasicsHealthIndicator` 把「业务视角的健康」暴露出去：自带的 `db`/`diskSpace`/`ping` 只说明进程和依赖活着，说明不了队列是不是快满了。下面用异步队列积压率模拟业务健康（`saturation ≥ 0.9` 即 DOWN）：

```java
@Component("basics")                       // Bean 名即 /actuator/health 里的组件名
public class BasicsHealthIndicator implements HealthIndicator {
    public Health health() {
        int queueSize = executor.getThreadPoolExecutor().getQueue().size();
        double saturation = Math.min(1.0d, (double) queueSize / 100);   // 队列容量 100
        return (saturation >= 0.9d ? Health.down() : Health.up())
                .withDetail("environment", properties.getEnvironment())     // withDetail 只在 show-details 打开时可见
                .withDetail("asyncQueueSaturation", String.format("%.0f%%", saturation * 100))
                .withDetail("auditRecords", auditLogger.totalRecords()).build();
    }
}
```

实测 `GET /actuator/health`：

```json
{"status":"UP","components":{
  "basics":{"status":"UP","details":{"environment":"dev","asyncPoolSize":4,"asyncQueueSize":0,"asyncQueueSaturation":"0%","auditRecords":1,"hint":"队列积压 ≥90% 判定为 DOWN"}},
  "db":{"status":"UP","details":{"database":"H2","validationQuery":"isValid()"}}}}          // 另有 diskSpace、ping
```

三个必须记住的语义：

- **`withDetail` 只在 `show-details=always`（或 `when-authorized` 且已认证）时可见**，否则只剩 `{"status":"..."}`；
- **返回 DOWN → 整个 `/actuator/health` 变 HTTP 503**，这就是 K8s 探针的输入：**就绪探针**失败摘流量，**存活探针**失败**重启容器**。判定条件要保守（「抖动即下线」比「多撑 30 秒」代价大得多），业务依赖不可用只适合做 readiness；
- **健康检查要快且无副作用**：它被 K8s 每几秒调用一次，里面有阻塞 IO 或重试循环就会把探针拖成超时。

### 自定义 InfoContributor 与自定义端点

`BasicsInfoContributor` 向 `Info.Builder` 写入 `basics` 段（appName/environment/features/contacts/javaVersion/os），与 `application.yml` 的 `info.app.*` 合并输出。价值在于**出问题时不用登机器就能确认「这个实例跑的是哪套配置」**：环境标识错了、功能开关没生效、上线拿到旧版本，一眼可辨；生产建议补 `git.commit.id`/`build.time`，但**别把内部主机名、构建凭证、数据库地址写进去**。

`BasicsEndpoint` 用 `@Endpoint(id = "basics")` + `@ReadOperation` 聚合审计记录、定时任务计数、线程池、缓存统计，从 `GET /actuator/basics` 访问。为什么不用 `@RestController`：`@Endpoint` **自动受 `exposure.include` 管辖**（开关在配置里，而不是「注册即可访问」）、**协议无关**（HTTP 与 JMX 双协议暴露）、能随管理端点挪到独立内网端口，且语义上把「运维观测」与「业务接口」分开——两者的权限模型、访问日志、限流策略都不同。注意 `audit.recent[].detail` 里带上了 `traceId`，**审计记录与访问日志能用同一个 traceId 对齐**。

实测 `GET /actuator/info` 与 `GET /actuator/basics`：

### 动态日志级别：不重启也能排障

线上怀疑某个类行为异常，第一反应不该是「加日志、重新发版」：

```bash
curl -s -X POST -H 'Content-Type: application/json' -d '{"configuredLevel":"TRACE"}' \
  http://127.0.0.1:8010/actuator/loggers/com.wkedong.springboot.basics.web.AuthInterceptor
# → {"configuredLevel":"TRACE","effectiveLevel":"TRACE"}     立即生效，无需重启
```

`configuredLevel` 是**显式配置的级别**，`effectiveLevel` 是**当前真实生效的级别**（继承父 logger 时两者不同）。排查完记得调回去——TRACE 挂在 QPS 高的接口上，日志盘几分钟就满。日志体系的三块拼图（`logback-spring.xml` 均已配置）：

- **profile 分支**：`<springProfile name="!prod">` 只打控制台，`<springProfile name="prod">` 控制台 + `RollingFileAppender`（`maxFileSize=10MB`、`maxHistory=7`、`totalSizeCap=500MB`，**磁盘可控**）。文件名必须是 `logback-spring.xml`：叫 `logback.xml` 会被 Logback 抢先加载，拿不到 profile 信息；
- **`%X{traceId}` MDC 关联**：格式里写 `[%X{traceId:-no-trace}]`，值由 `TraceIdFilter` 写入 MDC，同一请求的日志自动串联（实测两行同为 `[0dfcc1228f0f4a03]`：`AuthInterceptor - 鉴权失败：uri=/api/cache/stats ...` 与 `GlobalExceptionHandler - 业务异常：...`）。反过来，定时任务线程的日志是 `[no-trace]`——**异步/定时线程不继承调用方的 MDC**（ThreadLocal 不跨线程），要串联必须显式传递（如把 traceId 作为任务参数）；
- **日志里绝不能出现敏感信息**：token、密码、身份证、手机号、完整卡号，要么脱敏要么记哈希；`AuditLogger` 自带 `maxDetailLength=120` 截断，避免把整个请求体灌进日志。

### 优雅停机：让正在处理的请求跑完

配置只需两行：`server.shutdown: graceful`（收到 SIGTERM 后先停止收新请求，等旧请求结束）与 `spring.lifecycle.timeout-per-shutdown-phase: 20s`（最长等待时间，超时强制退出）。

**实测**（`/api/demo/slow?seconds=8` 发一个 8 秒请求，2 秒后 `kill -TERM`）：

```
HTTP 200 curl_time=8.018821s      ← 停机过程中正在处理的请求仍正常返回
body: {"code":0,"data":{"sleptSeconds":8,"costMillis":8005,"note":"若本请求在停机过程中仍正常返回，说明优雅停机生效"}}

日志：14:47:02.664 [SpringApplicationShutdownHook] GracefulShutdown - Commencing graceful shutdown. Waiting for active requests to complete
      14:47:08.682 [http-nio-8010-exec-7] [5bd00e7c665242ef] AuthInterceptor - 请求完成：GET /api/demo/slow -> 200 (8016 ms)
      14:47:08.728 [tomcat-shutdown] GracefulShutdown - Graceful shutdown complete
```

**同一窗口内的新请求被直接拒绝**（实测 curl 退出码 7、`HTTP 000`，即 connection refused）：Tomcat 收到 SIGTERM 后立即关闭监听端口，所以**关键前提是负载均衡已把这个实例摘掉**。K8s 的完整链条：

1. Pod 进入 `Terminating`，**同时**从 Service Endpoints 摘除（异步、有延迟）并发送 SIGTERM；Ingress/LB 需要几秒才感知摘除，这几秒流量仍会打到该 Pod——用 `preStop` 钩子（`sleep 5`）把「摘流量」与「开始停机」错开；
2. `terminationGracePeriodSeconds` 必须 **> `timeout-per-shutdown-phase`**，否则等待还没结束就被 SIGKILL，配置再漂亮也白搭；`AsyncConfig` 侧的 `waitForTasksToCompleteOnShutdown(true)` + `awaitTerminationSeconds(20)` 则保证队列里的异步任务也有机会跑完；
3. 优雅停机只管 **HTTP 请求**：消息消费者的 `stop()`、定时任务「正在跑的那一轮」要靠 `SmartLifecycle` 或消费端 ack 策略单独处理。

### 分层打包与工具链衔接

```bash
java -Djarmode=layertools -jar springboot-basics/target/springboot-basics-0.0.1-SNAPSHOT.jar list
# dependencies / spring-boot-loader / snapshot-dependencies / application
```

意义在于 **Docker 分层缓存**：`dependencies`（第三方 jar，几乎不变）与 `application`（你的 class，每次发版都变）分开拷贝，改一行业务代码只需重建最后一层，镜像推送从「几百 MB」降到「几百 KB」，配合 `COPY --from=builder` 分阶段构建即可（Dockerfile 细节见 `docs/29-容器化.md`）。

**与工具链的衔接**：Micrometer 是门面，`/actuator/metrics` 只是它的一个出口，接 Prometheus 需加 `micrometer-registry-prometheus` 并暴露 `prometheus` 端点，再由 Grafana 出图（见 `docs/27-指标监控与Grafana.md`）；`TraceIdFilter` + MDC 是单应用内的轻量版追踪，跨服务要换 Sleuth/OpenTelemetry 透传（见 [07-服务追踪](07-服务追踪.md) 与 `docs/21-*.md`）；容器里别靠 `kubectl logs` 看日志，把 prod 的滚动文件换成 stdout 采集进 ELK/Loki，按 traceId 检索。

**③ 优雅停机**：8 秒慢请求跑到第 2 秒时发 SIGTERM

```bash
curl -s -H 'X-Token: dev-token' "http://127.0.0.1:8010/api/demo/slow?seconds=8" &

# → HTTP 200 curl_time=8.018821s       旧请求跑完

# 日志：Commencing graceful shutdown. Waiting for active requests to complete → Graceful shutdown complete
```

## 思考点

- `/actuator/health` 返回 503 时，你希望 K8s 重启这个 Pod 还是只摘掉它的流量？把业务依赖（DB、下游服务、消息队列）写进 liveness 探针会发生什么？
- `show-details=always` 在 dev 很好用。如果 prod 忘了改回 `when-authorized`，`/actuator/health` 会泄露哪些信息？「反正没加认证」能当安全假设吗？`exposure.include=*` 又需要哪些前提才勉强可接受？
- 优雅停机的 20 秒等待、`preStop: sleep 5`、`terminationGracePeriodSeconds: 30` 三者叠加时，最坏情况 Pod 还能活多久？哪个值配错会导致请求被 SIGKILL 截断？
- 动态日志级别能救一次线上事故，也能被当 DoS 用。你会怎么限制它？（只对特定包开放？加 TTL 自动回滚？把 `loggers` 的 POST 纳入审计？）
