# 05 · 服务容错保护（Hystrix → Resilience4j）

> 模块：`service-consumer-ribbon-hystrix/`（7040）。
> 版本对照：本篇内联 Hystrix 旧写法与 Resilience4j 新写法，全量清单见 [08-升级迁移指南](08-升级迁移指南.md)。

## 学什么

分布式调用一定会遇到下游变慢/挂掉：如果消费方跟着一起挂（线程被拖死、故障沿调用链向上传染），
整个系统会雪崩。**熔断器**模式：像家里的保险丝——下游失败率超阈值时直接「跳闸」，
快速失败走降级逻辑（fallback），过段时间试探恢复（半开）。

本模块演示 producer 的 `/testHystrix` **故意睡 5 秒**，消费方设置 3 秒超时：
每次调用必然超时 → 触发 fallback 返回兜底文案 → 失败率堆积后熔断打开 → 后续请求直接快速失败。

## 2021.0.x 的写法迁移（对照学习，本次升级核心）

**旧（Edgware 版 Hystrix 写法）**：Hystrix 注解式——

```java
@HystrixCommand(fallbackMethod = "fallback")   // com.netflix.hystrix...
public String testHystrix() {
    return restTemplate.getForObject("http://service-producer/testHystrix", String.class);
}
public String fallback() { return "service-producer /testHystrix is error"; }
```

**新（develop 分支）**：Spring Cloud CircuitBreaker 抽象 + Resilience4j 实现——

```java
@Autowired
Resilience4JCircuitBreakerFactory circuitBreakerFactory;

public String testHystrix() {
    return circuitBreakerFactory.create("testHystrix").run(
            () -> restTemplate.getForObject("http://service-producer/testHystrix", String.class),
            this::fallback);          // fallback(Throwable t) 带上触发异常更利于排查
}
```

配置（`application.yml`，取代 `hystrix.command.default.*`；`bootstrap.yml` 已废弃、配置中心改走
`spring.config.import`，见 [02-配置中心](02-配置中心.md)）：

```yaml
resilience4j:
  timelimiter:
    configs:
      default:
        timeout-duration: 3s          # 对应 Hystrix 的超时
  circuitbreaker:
    configs:
      default:
        sliding-window-type: COUNT_BASED
        sliding-window-size: 10       # 统计最近 10 次调用
        failure-rate-threshold: 50    # 失败率 ≥50% 熔断打开
        wait-duration-in-open-state: 10s  # 打开 10s 后进半开试探
```

概念对照表：

| Hystrix 概念 | Resilience4j 对应 |
| --- | --- |
| `@HystrixCommand(fallbackMethod)` | `CircuitBreaker.run(supplier, fallback)` |
| 线程池隔离（默认） | 信号量隔离（默认；`resilience4j.thread-pool-isolation.*` 可选） |
| 超时 1s 默认 | TimeLimiter 默认 1s（demo 显式 3s） |
| Dashboard 线程 | Actuator `/actuator/circuitbreakers`、`/actuator/circuitbreakerevents` |

> 为什么要换：Hystrix 2018 年起进入维护态，Netflix 官方推荐 Resilience4j；
> Spring Cloud 2020.0 移除 Hystrix 相关 starter，2021.0 的容错只走 CircuitBreaker 抽象。

## 动手验证

```bash
curl http://localhost:7040/testHystrix
# 等 3 秒（TimeLimiter 上限 3s，producer 睡 5s）→ 返回 "service-producer /testHystrix is error"

# 更短的超时演示：/resilience/timelimiter 用 1s 上限（resilience4j.timelimiter.instances.slowCall）
curl http://localhost:7040/resilience/timelimiter
# → 【降级】producer 响应超过 1s 上限（ExecutionException），costMillis≈1005

# 连打 10 次触发熔断后再调用，响应应变成「秒回」：
for i in $(seq 1 12); do curl -s -o /dev/null -w "%{time_total}\n" http://localhost:7040/testHystrix; done
# 前几次 ~3s（真实超时），熔断打开后接近 0s（快速失败）

# 观察熔断器状态：
curl http://localhost:7040/actuator/circuitbreakers | python3 -m json.tool
# state: OPEN / HALF_OPEN / CLOSED；events 端点可看状态迁移历史
```

## 思考点

- fallback 应该「便宜且确定成功」：查缓存、返回默认值、入队异步处理，而不是再发一次慢调用；
- 熔断是**按实例统计**的：demo 里调 10 次即可打开，生产环境的阈值要与流量匹配；
- 把 `/actuator/circuitbreakerevents` 接到告警系统，比肉眼看 Dashboard 更有价值。
